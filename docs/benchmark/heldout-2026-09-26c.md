# Held-out generalization report, 2026-09-26 (draw C)

This is the third held-out draw. The first two are [heldout-2026-09-24.md](heldout-2026-09-24.md)
(draw A) and [heldout-2026-09-24b.md](heldout-2026-09-24b.md) (draw B). Draw C is larger, broader
and harder than both: 90 new held-out inputs from 88 source records, across 40 formats in 14
families. It measures OpenReadout 0.1.0 on a development build, whose reader
code is `main` at `7c0ad6bd`. The binary is a release build. The same build was also re-run over
every earlier held-out input, which makes 171 inputs in all. No model was called.

The rules of [heldout.md](heldout.md) apply. **Do not fix a reader on these files.** Reproduce each
finding below on a new public file first; that file joins the development corpus with its own
provenance entry. The held-out file only confirms afterwards that the fix generalizes.

## Method

As before, with three additions.
- **Questions first.** The 87 new questions (`ho-c-*`) were committed in `d415ecd3`. That was before
  OpenReadout was run on any draw-C file. 62 are lookups and 25 are analysis tier. The answers come
  from the held-out oracles, the depositors' exports and facts computed with third-party readers
  (`evals/heldout_draw_c.py`), cross-checked by a second reader where one exists. The held-out split now
  has 191 questions.
- **Ground truth.** The same third-party readers as the development corpus were used. Where a
  family had no oracle for these files, the oracle scripts were extended:
  - `oracle/plate.py` gained independent readers for Gen5 text grids, BMG CLARIOstar CSV and EnVision
    CSV, because allotropy rejects all three;
  - held-out JASCO files get jws2txt (MIT) as ground truth;
  - held-out GenePix files go to `gpr_oracle.py`;
  - Shimadzu files without an export go to chromConverter (GPL, run as a black box).
- **Assurance.** `evals/heldout_probe.py` now records each file's `assurance` block. The new
  `evals/heldout_summary.py` tabulates the run by draw, family and assurance level. It applies the
  adjudication of every disagreement, recorded in
  [heldout-2026-09-26c-classes.json](heldout-2026-09-26c-classes.json).

Two comparison settings changed after the first run, and they are disclosed here. First, the JPEG
whole-slide images (NDPI, SVS) and the WiRE map's white-light JPEG were given `lossy = true`, as every
earlier held-out JPEG slide and WiRE map has. The SVS then agrees within the lossy tolerance. Second,
the draw-A Axioscan CZI oracle was regenerated with main's fixed `oracle/czi_levels.py`, which now
handles factor-3 pyramids. That file now passes, so its earlier failure was an oracle error. Raw
results: [heldout-2026-09-26c.json](heldout-2026-09-26c.json).

Depth of the 74 draw-C agreements:
- 71 compared values: planes, samples, peaks, events, Cq values, plate values or GPR cells.
- 3 compared structure only. For the 25088 × 37632 NDPI slide, the plane is too large for the hash
  oracle, so only its geometry was compared. For two `.eds` runs saved without results, only the
  plate setup was compared.

**Question level.** The command an agent would use was run once per new question. This was a tool
check, not a benchmark run. The output holds the answer for 84 of the 87 questions. One of those 84
(the WiRE map's mean spectrum) needs several steps and was not verified end to end. Two cannot be
answered: the Berkeley EMD is refused (C-G2), and the BMG scan returns no values (C-H1). Separately,
`run.py preflight --split heldout` stages all 191 held-out questions and flags 3 of them. Those three are the EMD refusal (exit 6), plus `check` exit 4 on the
FT-ICR mzML and on the BMG export (C-L2, C-H1).

**Speed.** Every draw-C file finished `info` in ≤ 0.09 s and `check` in ≤ 0.44 s. `info --view format`,
`info`, `check` and `info --view full` over all 171 inputs took 16 s of wall time. No command panicked, and
every file was detected as its manifest format.

## Assurance: does `--strict` catch the errors?

Each file's `assurance.level` from `info` (docs/assurance.md) is set against its adjudicated
verdict. Files the reader refuses (exit 6) have no assurance block.

| verdict (all 171 inputs) | validated | partially validated | unvalidated | refused (none) |
| --- | --- | --- | --- | --- |
| agree | 71 | 56 | 16 | 0 |
| oracle / converter error | 2 | 4 | 1 | 0 |
| reader error | 1 | 1 | 2 | 0 |
| unresolved | 1 | 0 | 0 | 0 |
| refused (gap) | 0 | 0 | 0 | 4 |
| self-consistency only | 0 | 3 | 1 | 0 |
| no oracle | 7 | 0 | 1 | 0 |

- **Recall.** `--strict` would refuse 2 of the 5 reader errors and unresolved cases: the Shimadzu
  traces (N-L1) and the BMG scan (C-H1). Both are errors where values are missing or unscaled. It
  misses the other three. The EnVision mode label (C-M1) is `partially_validated` and the JASCO
  measurement time is `validated`; both are metadata errors. The UNICORN peak heights are
  `validated`, and that case is unresolved. For value errors, then, recall is 2 of 2. For metadata
  errors it is 0 of 2, because the assurance signal does not cover how a field is labelled or which
  field is used.
- **Precision.** 2 of the 19 `unvalidated` files with an independent verdict are reader errors
  (11 %). In draw C alone, 1 of 11 is.
- **The price.** 17 files that are read correctly are `unvalidated`, and `--strict` would refuse
  them. 10 of them are in draw C: the SER TEM image, the Intan RHS, the JEOL 400 MHz FID, the COSY,
  three OMNIC files, the Orbitrap ID-X run (right apart from the converter convention), the FT-ICR
  mzML and one Image Lab blot. Their variants have simply not yet been confirmed on a development
  file.
- **Right or refuse.** All four variants no third-party reader supports either were refused cleanly
  (exit 6 with an actionable hint), not read wrongly: DCIMG 0x2000000, Berkeley EMD and two older
  JASCO layouts.
