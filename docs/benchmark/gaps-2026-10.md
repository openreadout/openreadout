# Validation gaps, October 2026

This report covers one round of work on the places where OpenReadout says it is not sure: formats
with `low` or `medium` confidence, and variant features the development corpus reaches but no
independent reader confirms (the table in `book/src/project/health.md`). It says what was closed
and with what evidence, and for each gap that remains, what evidence would close it.

The confidence rubric is in `docs/assurance.md`. In short: `medium` needs 3 confirmed files from 2
depositors (or 3 confirmed versions); `high` needs 5 confirmed files from 3 depositors with 2
versions, no failure on a development or held-out file, and either a published specification or
vendor documentation, or else 10 confirmed files from 5 depositors.

No held-out file or reserved record was used. Every new file comes from a record that no held-out
entry uses (`cargo xtask heldout-check`), with its licence recorded in `corpus/manifest.toml` and
its provenance in `docs/provenance/`.

## Variant features closed

- **mzML and mzXML exports read as inputs.** The ProteoWizard test exports and the MTBLS225 mzXML
  had no oracle of their own, so their writers, instruments and chromatogram kinds were unconfirmed.
  pyteomics now reads each one (51 files); all agree.
- **SRM chromatograms rebuilt from spectra** now count as a check of the spectra (as they already
  did for Thermo), which confirms Sciex QTRAP MRM (`scan type MRM`, `stored SRM`,
  `generation QTRAP`).
- **Gen5 experiment files** (`container gen5-experiment`, Cytation 5, Synergy HT, Gen5 1 and 2) and
  the **Thermo PDA and UV channels** of MTBLS773 were compared with independent exports by
  `plate_binary` and `thermo_detectors`, but those tests wrote no results line. They do now.
- **RAS `2θ/θ scan` and RASX `TwoThetaTheta scan`**: geddes refuses the two files that carry them;
  xrayutilities and FAIRmat's reader now provide trace ground truth.
- **Gamry `ZCURVE` of the aborted EIS run**: gamry-parser refuses it; impedance.py reads it.
- **LightCycler 480 `.ixo`**: the `ixo` dialect, amplification records and the LED and Xenon lamp
  instruments are confirmed. Melt curves stay unconfirmed (see below).
- **Zetasizer size records**: Z-average, PdI and intensity peaks are decoded and confirmed for
  writers 7.10, 7.12 and 7.13.

## Corrections made on the way

- **Health page and audit disagreed.** `cargo xtask health` decided "validated" with its own rule,
  which ignored vendor-stored results and tracked fields. It now uses the audit's rule, so the
  health page lists tracked fields (acquisition time, instrument model) that no oracle has checked.
  The table looks longer, but it is the same evidence counted the same way as the generated tables.
- **Stored peaks over-claimed.** Chromeleon's stored-peak reproduction validated every trace
  feature of an archive, including pressure and flow signals that no peak was found on. The
  results line now names the features of the integrated signals, and only those count.
- **Reader errors found by the new files and fixed on them:** RASX reciprocal-space maps returned
  scans in text order; imzML spectra that state their level only in `fileContent` were level 0, and
  `check` passed a file whose arrays differ in length; Empower exports with one field per line were
  refused; a Zetasizer sample name was empty when a record's material block starts with 2; the
  LightCycler 480 model was taken from a field one lab filled with a serial number.

## Known disagreements kept in the corpus

- `cmbx-lim-ketoisophorone-standards` (Chromeleon): 82 of 84 stored peaks reproduced. The two
  others are a peak that starts at the first sample and its rider; their areas differ from ours by
  the same amount in opposite directions, so the rider's skim line is not the straight line between
  its stored ends. Not explained. The archive records a stored-result failure, which keeps
  `chromeleon` at `medium` although it now has 13 confirmed files.
- `mtbls2240-bal-214-ecoli` (Sciex): a scheduled MRM file without stored windows. The reader now
  takes each window from the method (expected time ± half the 240 s detection window), and values
  inside the windows agree, but Analyst decides the edge cycles at each transition's own time within
  the cycle, which the file does not record. The file carries `oracle_skip` and the layout
  `scheduled MRM, method windows` stays unvalidated, so `--strict` refuses those spectra.

**Held-out counts.** The rubric reads held-out pass and fail counts stored in
`corpus/assurance/evidence.json`. They were recorded at the first public release, from a run over
the 74 inputs of draws A and B, and have not been refreshed since. The CZI failure in them later
turned out to be an oracle error, and the latest run over all 292 held-out inputs passes all 13 CZI
files. That run also records new failures for `oib`, `openlab-cds`, `sciex-wiff` and more for
`thermo-raw`, `shimadzu` and `plate`. This round did not refresh the counts: the latest run is a
re-measurement after fixes, and the counts are raw corpus-test results that do not tell an oracle
error from a reader error. What would settle it is the next held-out draw, with its counts written
by `assurance-audit refresh --heldout`, and a decision on whether adjudicated oracle errors count as
failures. Until then `oib` is `high` on development evidence while the latest run records one OIB
reader error (D-H4).
