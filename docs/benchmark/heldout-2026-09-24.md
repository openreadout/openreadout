# Held-out generalization report, 2026-09-24

This report covers OpenReadout 0.1.0 at commit `8f41b27`, release build. It was run on the 54 held-out inputs of `corpus/manifest.toml` (tier `heldout`, policy in [heldout.md](heldout.md)). No model was called.

The rule for this report: **do not fix a reader on these files.** Every finding below should be reproduced on a new public file first, and that file is added to the development corpus with its own provenance entry. The held-out file is only used afterwards, to confirm that the fix generalizes. If no other file shows the problem, the held-out file moves to the development corpus and a replacement is found ([heldout.md](heldout.md), rule 2).

## Method

- **CLI probe** (`evals/heldout_probe.py`): runs `info --view format`, `info`, `check` and `info --view full` (all `--json`) on every input, and compares `info` field by field with `corpus/oracle/heldout/<id>.json`. The compared fields are image count, sizes, pixel type, physical sizes, channel names, trace sweeps/samples/rate, table rows and scan count. Raw results are in [heldout-2026-09-24.json](heldout-2026-09-24.json).
- **Deep comparison** (`cargo test -p openreadout-corpus-tests --features corpus --profile corpus heldout`): the same check as the development corpus's `corpus_matches_oracle`. It compares xxh3 hashes of every plane (up to 64 per image), of every sweep × channel block, of FCS event matrices and of plate values. It compares every scan of an MS run against the depositor's mzML/mzXML (peaks, precursor, charge, polarity, centroid flag). It records the result and never fails.
- **Oracles**: the same third-party readers as the development corpus: czifile, nd2, liffile, tifffile, oirfile, Bio-Formats (black box, OIB/ZVI), h5py, mrcfile, dm3_lib, ncempy (black box, SER), flowio + fcsparser, pyabf, nmrglue, jcamp, pyteomics on depositor exports, rainbow-api (black box) + Aston, scipy netCDF and allotropy.
- **Staging**: `uv run python run.py preflight --split heldout` stages all 62 held-out questions. 61 pass `info --view format` + `check`; the one flagged is Exploris 480, finding H1.
- **Questions first**: the 62 held-out questions were written from the oracles and depositor exports before OpenReadout was run on any held-out file.

Every file was detected as the right format, `info` exited 0 on all 54, and no command panicked. `check` exited 4 on two intact files (H1, M3). Speed: `info` took ≤ 0.021 s and `check` ≤ 0.24 s on every file. All four commands over all 54 files took 2.6 s of wall time. The deep comparison of the whole held-out set took 6 s.

Development-corpus baseline for context: `corpus_matches_oracle` passes on every development file. On held-out files, 46 of 54 (85 %) agree with their oracle, or 46 of 53 (87 %) excluding the file that has no oracle. The disagreements concentrate in newer or unusual variants of formats that pass on the development corpus: an Orbitrap Exploris run, a Q Exactive HF PRM run, a Bio-Formats JPEG OME-TIFF, a comma-delimited i-control export, and an RGB ND2.

Every fix below was developed on new public files added to the development corpus (none from a held-out source record; `cargo xtask heldout-check` passes). The held-out files were not opened; rerunning the probe and the held-out corpus test on them is the confirmation step of rule 2.

## What the held-out questions will show

The 62 questions (`evals/questions/heldout.jsonl`) were written before this probe was run. Four of them touch the problems above. `ho-ana-ms-raw-exploris-tic` needs spectra from the Exploris file (H1). `ho-ana-mic-nd2-rgb-red-mean` expects the vendor's red channel (M1). `ho-ms-raw-prm-collision` and `ho-ana-ms-raw-prm-precursors` read PRM metadata that agrees with the export, so M2 should not affect them. `ho-mic-ometiff-prostate-size` asks only for the dimensions, which are right. H2 would show up in any pixel question about that file.

## Reproduce

```bash
cargo xtask corpus fetch --tier heldout
cargo build --release -p openreadout
HELDOUT_REPORT=/tmp/heldout-corpus.jsonl cargo test -p openreadout-corpus-tests --features corpus --profile corpus --test corpus heldout -- --nocapture
cd evals && uv run python heldout_probe.py --binary ../target/release/openreadout --corpus-test /tmp/heldout-corpus.jsonl -o ../docs/benchmark/heldout-<date>.json
uv run python run.py preflight --split heldout
```
