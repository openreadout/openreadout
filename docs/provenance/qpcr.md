**Method and observations** (each file listed with Python's `zipfile`, members read as text):
- `.eds` is a zip in three layouts. (a) *SDS layout* (`Manifest.mf` "Experiment Document Specification" 1.x): `apldbio/sds/` with `experiment.xml` (name, run state and times in Unix milliseconds, experiment type, samples, detectors = targets with reporter and quencher dyes, instrument type id, block and plate type, software version under `ExperimentProperty type="RunInfo"`), `plate_setup.xml` (rows, columns, feature maps `sample` and `detector-task` keyed by zero-based well index; `Wells/Well/IsOmit`), `tcprotocol.xml` (stages with a stage flag `PRE_CYCLING`/`CYCLING`/`DISSOCIATION`/..., repetitions, steps with one temperature per block zone, hold time in seconds, ramp rate, `CollectionFlag` 1 = read during the step, 2 = continuous read during the ramp), `analysis_protocol.xml` (analysis settings as name/typed-value pairs: detector `Threshold`, `AutoCt`, `BaselineStart`/`BaselineStop`, `AutoBaseline`, per-well `IWellSettings` overriding them, `EndogenousControl` and `Calibrator` for ΔΔCt), `multicomponentdata.xml` (per well the dye list and, per dye, the multicomponent signal of every collection point; the collection points `[Stg:s Cyc:c Stp:p Pt:n]` and per-point sample temperatures), `analysis_result.txt` (tab-separated: one header line, then per well × target a result line — well index, sample, target, task, Ct, mean Ct, Ct SD, ΔCt, quantity, mean quantity, quantity SD, amplification status, Cq confidence — followed by lines `Rn values` and `Delta Rn values` with one value per cycle, and in ΔΔCt experiments a `DDCT Values` line), `meltcuve_result.txt` (spelled so by the vendor: per well × target the Tm list, then `Sample Temperatures`, `Rn values` and `Derivative` lines). Genotyping experiments write a different `analysis_result.txt` header (`Call`, `Marker Name`, `RnX`, `RnY`). (b) *7500 / StepOne layout* (7500 Software v2.x): `apldbio/sds/multicomponent_data.txt` (header "StepOne v2.0 MulticomponentData"; records `WELL CYCLE DYE MSE SIGNAL` followed by pure-dye coefficients on continuation lines) instead of `multicomponentdata.xml`, raw images under `images/`, member names sometimes with backslashes (`APLDBIO\SDS\CALIBRATIONS/background.ini`). (c) *JSON layout* (`Manifest.mf` specification 2.0.0, "qPCR File API"): `summary.json`, `setup/plate_setup.json` (samples, targets with reporter/quencher, wells with target assignments and tasks), `setup/run_method.json` (stages, steps, hold, ramp, collection profiles), `run/run_summary.json` (instrument, serial numbers, operator, times), `primary/multicomponent_data.json` (per well, per dye fluorescence per collection point, plus temperatures), `primary/analysis_result.json`.
- Files whose run was set up but not analysed (no `analysis_result.txt`) or that keep only raw CCD images (`images/*.tiff`, no multicomponent data) are opened for their setup; the missing parts are reported.
- `.pcrd` (Bio-Rad CFX Maestro): every public sample is a zip with a single member `datafile.pcrd` whose general-purpose flag bit 0 (encryption) is set. The key is not public; per rule 4 of the clean-room policy the format is detected and refused with exit 6 and a hint to export RDML from CFX Maestro. No key or password was searched for or used.
- `.rex` (Rotor-Gene Q software, "REX 3.15"): plain XML; samples with tube positions, channel definitions, raw channel readings per cycle.
- Roche LightCycler 480 (`.ixo`, `.lc`): no public sample with a redistribution licence was found (Zenodo, Figshare, GitHub searched 2026-09-23); not implemented. LightCycler 96 data reach us as vendor-written RDML.

## 2026-09-24 — validation and our analyses (Richard Zimring with Claude as assistant)

**Corpus files used:** the 18 files above. No new prior art; the analysis methods are textbook (least-squares baseline, threshold crossing, 2^−ΔΔCq with the Pfaffl efficiency correction, standard-curve efficiency (10^(−1/slope) − 1) × 100).

**Readers against the oracles** (`cargo test -p openreadout-corpus-tests --features corpus --test qpcr`): all 18 files pass. Every RDML reaction's sample, target, dye, task, Cq, excluded flag and Tm match rdmlpython 1.7.2, and so do the point counts and sums of its amplification and melt data (relative 1e-9). Every `.eds` well's Cq, undetermined call, Tm list, Rn/ΔRn and melt sums, and its sample/target/task match the vendor's own result files. The program cycles and the read temperature also match (the read temperature is compared only when a single step collects data). qslib's multicomponent signals match per well and dye. Each `.rex` reading's sums match ElementTree. The `.pcrd` exits 6. Every file exported with `export --to rdml` passes rdmlpython's schema validation and reads back with the same Cq values.

We match the vendor's Cq only when the file records the vendor's threshold and baseline, or they can be recovered from it. The method evolved to get there:
1. First version: a fixed 3–15 baseline, a 10 SD threshold and linear interpolation. Median differences were 0.3–1 cycle even on files that record the threshold.
2. Interpolate the crossing in log(fluorescence), because amplification is exponential between reads.
3. Automatic baseline: end the window three cycles before the first Cq estimate, with earlier windows for curves that rise inside cycles 3–15.
4. SDS/7500 layouts store Rn and ΔRn per cycle, so the vendor's baseline line is recovered exactly as Rn − ΔRn (a line within relative 1e-5). Their threshold is not stored per well, so it is recovered as the median over wells of the log-interpolated ΔRn at the vendor's Ct (per target). This is inferred from the stored curves, not from a specification.
5. RDML `quantFluor`/`bgFluor`/`bgFluorSlp` are used when present, and `vendor_threshold_used` records whether the file gave the threshold.

Files without a recorded threshold (Bio-Rad CFX, LightCycler 96 and StepOne RDML) fall back to the 10 SD automatic threshold. Their vendors use other thresholds or methods (for LightCycler software most likely a second-derivative maximum; the file does not say which), so those comparisons measure method differences, not reader errors. `docs/formats/qpcr.md` says so.

**ΔΔCq** (`analyze qpcr --ddcq`, `eds-7500-abhd17c-ddct`, reference 18s, calibrator Lenvatinib/Vector): ΔCq and RQ match the vendor's `DDCT Values` lines for all four samples (for example `ABHD17C OE`: ΔCq 14.0921 vs 14.092075; RQ 48.9879 vs 48.9879; `Vector`: RQ 1.1302 vs 1.1302301).

**Standard curve** (`analyze qpcr --standard-curve`, `eds-qs7pro-tb18s-stdcurve`, 18 standard wells): slope −3.27912 (vendor −3.2791, stored rounded), efficiency 101.81780 % and R² 0.999204. Both are identical to the vendor's stored values (`extensions/am.sc/standard_curve_result.json`).

## 2026-09-24 — "Undetermined" wells in SDS-layout `.eds` (QuantStudio 6/7 Flex, 12K Flex, ViiA 7) and the Amp Status codes

**Problem (N-H1 of the second generalization report):** QuantStudio 6/7 Flex and ViiA 7 files returned a Cq equal to the last cycle (40 or 50) for wells the vendor software reports as "Undetermined". Those Cqs were unflagged, so means and 2^−ΔΔCq were wrong.

**New development files** (none from a held-out source record). Each is paired with the vendor's own Results export of the same run (`.xls`, written by the instrument software):
- `eds-viia7-npff-ddct` + `eds-viia7-npff-ddct-xls`: ViiA 7, 384-well, "QuantStudio 6 and 7 Software; 1.3", comparative Ct, 156 wells, 11 Undetermined (Figshare 21205928 / 21202280, CC-BY-4.0);
- `eds-qs7flex-tac-hmsc-stdcurve` + export: QuantStudio 7 Flex, 384-well, software 1.3, standard curve, 150 wells, 3 Undetermined (Zenodo 4598136, CC0);
- `eds-viia7-hmsc-siexo-stdcurve` + export: ViiA 7, 384-well, standard curve, 105 wells, 7 Undetermined (all NTCs) (Zenodo 4598136, CC0);
- `eds-qs12k-tdmmc-stdcurve` + export: QuantStudio 12K Flex 1.2.2, 384-well, 288 wells, 1 Undetermined, with a `Cq Conf` column (Harvard Dataverse doi:10.7910/DVN/QE5CEQ, CC0);
- `eds-qs35-npff-mtrna-ampstatus` + export: QuantStudio 3, "QuantStudio 3 and 5 Software 1.4.3", 96-well, 86 wells, 1 Undetermined, `Amp Status` and `Cq Conf` columns (Figshare 21205784, CC-BY-4.0).

**Prior art consulted:** none. The rule comes from the files and the vendor exports alone.

**What was inferred from what:**
- In every file, `apldbio/sds/analysis_result.txt` stores a well the export calls "Undetermined" as `Ct` = `40.0`, which equals the cycling stage's `NumOfRepetitions` in `tcprotocol.xml` (40 in all five programs). The column never holds the text "Undetermined", NaN or −1. The number of wells with `Ct` equal to the cycle count equals the export's Undetermined count in every file (11, 3, 7, 1, 1), and no other well has it. Real Cqs are interpolated fractions: the highest is 39.66, and none is a whole number at the cycle count.
- **Rule:** in the SDS and 7500 text layouts, a `Ct` ≥ the program's cycle count (the repeat count of the cycling stage) means no Cq. The result is `cq` = null, `cq_status` `undetermined`, and the stored value is kept as `cq_stored` plus the flag `ct_at_cycle_count`. Without a program, the value is kept, with a note.
- The vendor's replicate mean (`Avg Ct` / export `Ct Mean`) leaves out undetermined replicates. For example, `eds-viia7-npff-ddct` I13/I14/I15 (Cidea, sample 4763) has Ct 32.7826, Undetermined, 25.1048 and Ct Mean 28.9437 = the mean of the two. Our aggregates do the same by default.
- **`Amp Status`** in QuantStudio 3/5 files: over 86 wells of `eds-qs35-npff-mtrna-ampstatus`, `1` pairs with the export's "Amp" 75 times, `0` with "Inconclusive" 10 times and `-1` with "No Amp" once. The earlier mapping (0 → not amplified, −1 → inconclusive) was wrong and is corrected: 1 → `amplified`, 0 → `inconclusive`, −1 → `not amplified`. `Cq Conf` is 0 for the undetermined well.
- **Our own Cq** (`analyze qpcr --cq`) follows the same rule. A curve that never crosses the threshold, or crosses it only at or after the last cycle, gets `computed_cq_status` `undetermined` and no `computed_cq`. The vendor still calls Cqs inside the last interval (39.66 of 40 cycles in `eds-viia7-npff-ddct`), so a crossing between the last two reads stays a Cq. `cq_comparison.both_undetermined` now counts the vendor's undetermined wells; before this change they were compared as Cq 40.
## 2026-09-24 — Zip containers read by the shared `openreadout_core::zip`

**Scope:** the crate-private zip reader is replaced by one shared module in `openreadout-core` (`zip.rs`), used by qPCR (RDML, `.eds`, `.pcrd`), OpenLab CDS (`.dx`, `.rx`) and zipped OME-Zarr stores. No new interpretation of any format. The shared reader is the union of the three copies: central directory with ZIP64 records, case-insensitive and exact name lookup, stored and deflated members checked against their CRC-32, partial reads of stored members, a deterministic writer. Hardening over the copies: every offset and length is checked against the file size before it is read (a range past the end is exit 4, not an I/O error); a declared member count the central directory cannot hold is corrupt; inflation is bounded by the member's declared size (`miniz_oxide::inflate::decompress_to_vec_with_limit`, so a zip bomb stops there instead of pre-reserving or growing past it); the archive is read through one byte source with positional reads instead of a file opened per member. Fuzz target `core_zip`; unit tests flip and truncate every byte of a small archive.

**Prior art consulted:** PKWARE APPNOTE.TXT (public specification), as before. No new corpus files.

**What was inferred from what (`.lc96p`):**
- `rdml_data.xml` names samples by a GUID `id`; the name the LightCycler 96 software shows (and the xlsx lists: `Hm_1`, `DIP 24 h_1`) is the sample's `<description>`. Rule (all RDML files): when a sample `id` is a GUID (8-4-4-4-12 hex digits) and its description is non-empty and unique among the samples, the description is the sample name; the GUID stays in `extra.samples[].id`.
- `app_data.xml` maps each run's `react id` to a `factGraph id` (one per target, with `targetId` and `isExcluded`). `calculated_data.xml` holds per `factGraph` a `call` (`Positive`, `Negative`), and under the analysis instance `relQuantDataSource` rows (graph id, `cq`, `epf`) and `relQuantStatisticalRow` rows (graph ids of one replicate group, `cqMean`, `cqError`). Checked on the three files against the xlsx: every `cq` equals the RDML `<cq>` and the xlsx Cq (108 wells); every `cqMean`/`cqError` equals the xlsx Cq Mean / Cq Error at its printed precision (36 groups), and `cqError` is the sample standard deviation (n − 1) of the group's Cqs. Our mapping: `cq_mean`, `cq_sd` from the statistical rows, `amp_status` from `call` (`Positive` → `amplified`, `Negative` → `not amplified`, other text kept), `excluded` from `isExcluded`.

**What was inferred from what (`.ixo`):**
- The file is XML (`<objectstream signature="IXOS" version="1">`, CRLF) followed by one line `$` + four 8-hex-digit groups after `</objectstream>` (a checksum or signature we do not verify; the XML is parsed up to `</objectstream>`).
- Objects are `<obj name class version>` with `<prop name>` values and `<list name count>`; `count` equals the number of children in every list of the four files.
- `HTCRun`: `StartTime`, `EndTime`, `InstrumentName`, `InstrumentID`, `Technician`; `Protocol/Programs` lists `HTCRunProgram` (name, `Cycles`, `AnalysisMode` `Quantification` / `Melting Curves`, segments with `Target` °C, `Hold` s, `Slope` °C/s, `AcquisitionMode` 0 none, 2 continuous (the melt ramps), 1 single (the Cycling program's 58 °C segment: one read per cycle)); `Container` `HTCBlockType` (`RowCount` 8, `ColCount` 12); detection channels `HTCChannel` named `<excitation>-<emission>` nm.
- Acquisition store: `Cycles` lists `TCycle` (`Program` zero-based index into the program list, `Segment`, `Cycle` zero-based) with `THTCFloAcquisition` items (`Time` ms, `Temp` = `$` + 16 hex digits of a big-endian f64 in °C, `Channel` index into the detection format, `FloPoints` = one f32 per plate position). For the Quantification program each cycle holds one acquisition per channel (45 × 2); melt programs hold one TCycle with 102 and 190 acquisitions alternating the channels.
- Well order: `FloPoints` index k is plate position k (row-major, `Pos` k). Evidence: in all four files every well the vendor analysis calls positive (`Call` 2, 40 wells per file) rises 1.74–1.97× from cycles 4–8 to the last three cycles in channel 498-640, and every well it calls negative (`Call` 0, 56 per file) stays within 0.92–1.05×.
- Samples: `SampleInfoList` holds one `SamplePropInfo` per position (`ContainerPosition`) with `Sample Name`, and per channel (`ChannelIdx`) `Target Name`, `Quantification Sample Type` (`qsUnknown`, …), `Concentration`, `Target Type` (`dtNone`, …).
- Analyses: `Legacy Absolute Quantification Analysis` (named "Abs Quant/2nd Derivative Max for All Samples") holds `QuantSampleB` per position: `IsIncluded`, `Pos`, `Call`, `CrossingPoint` (0 when `Call` is 0), `CalcConc`, `ConcStatus`; the analysed channel is `ChannelRatio NumeratorXWL/NumeratorEWL` (498/640) and program `ProgramInfo SelectedProgram` (1 = Cycling). We report `cq` = `CrossingPoint` for `Call` ≥ 1 and undetermined for `Call` 0; `Call` 1 is reported with its Cp and `amp_status` `uncertain` (only the MIT parser's reading; no such well in the corpus). Other analysis classes and the calculator stores (`DARZ`/`FORM` binary arrays: smoothed melt curves) are listed, not decoded.
- Our own Cq does not reproduce the vendor's Cp (method difference, measured in `crates/openreadout-corpus-tests/tests/qpcr_roche.rs`); the vendor's algorithm is not public and was not reverse-engineered. Tried on the four files and not adopted: the argmax of the discrete second difference with parabolic interpolation (median +0.41 to +0.54 cycles from the vendor Cp) and the second-derivative maximum of a fitted 4-parameter logistic (+1.5 to +1.6).

**`.lc96p` finding — the RDML `cq` of non-positive reactions.** Tabulating the RDML `<cq>` against the software's call over the three new files and `rdml-lc96-bactxy`: every `Positive` call has a plausible Cq (max 37.97 of 50 cycles); `Negative` and `Invalid` calls carry 100 (121 reactions) or arbitrary numbers (1.56, 2.93, 72.55 of 50 cycles; 370 reactions). The xlsx lists exactly the positive wells. Before this change those numbers were reported as determined Cqs (e.g. 60 wells of Cq 100 in each `.lc96p`, target means of 97.4). Rule: with the LightCycler 96 members present, a reaction whose call is not `Positive` has no Cq (see `docs/formats/qpcr.md`).

**Our automatic-threshold Cq and decaying curves.** On the LightCycler 480 QC runs, `analyze qpcr --cq` called 31 Cqs on wells the vendor calls negative (11, 6, 8, 6 per file). All were monotonically decaying raw curves (photobleaching, e.g. 568 → 521 over 45 cycles) whose residual after the baseline line crossed 10 SD. Rule added to the automatic threshold only: a crossing counts when the stored fluorescence after it rises above the baseline-window mean by at least the threshold. Effect over the whole qPCR corpus (`tests/qpcr.rs`, `tests/qpcr_roche.rs`): LightCycler 480 false Cqs 31 → 1; `rdml-lc96-bactxy` Cqs of ours on vendor-negative reactions 217 → 127; no vendor Cq lost in any file ("only vendor" unchanged everywhere), no change on files with a recorded threshold.

## 2026-09-26 — StepOnePlus Results exports: the automatic baseline window of each well

**New development files** (no held-out record): StepOnePlus runs (`.eds`, 7500 layout: `apldbio/sds/analysis_result.txt` with Rn and ΔRn per cycle) paired with the depositors' Results exports (`.xls`, StepOne Software, wells named `A1`) — Zenodo 18006983 (Jacobs & Nowak-Sliwinska 2025, "Drug combinations for colorectal cancer treatment_qPCR TAEC", CC-BY-4.0).

- The exports list per well `Automatic Ct`, `Ct Threshold`, `Automatic Baseline`, `Baseline Start`, `Baseline End`, `Tm1`–`Tm3`. With `Automatic Baseline` 1 the window differs from well to well (3–13, 3–39, 1–2, 3–8 …), while `analysis_protocol.xml` holds one setting (`BaselineStart` 3, `BaselineStop` 15). We reported that setting as `baseline_start`/`baseline_end` of every well: a window the vendor did not use.
- `Rn − ΔRn` is the vendor's baseline line (already used for our Cq). A least-squares line through the stored Rn of cycles s…e reproduces that line (intercept and slope within 1e−6 of the Rn scale) for exactly one window in 238 of 240 wells of three runs, and that window is the export's `Baseline Start`–`Baseline End` in every one of them; one well has no three-point window (the export says 1–2: a two-point window) and one flat, undetermined well matches two windows. Over all 8 runs added (6 of this record, 2 of Figshare 30581381, CC-BY-4.0: StepOnePlus runs with their Results exports, `eds-stepone-caco2-*`), 572 of 574 windows are recovered and equal the export; 2 are left empty.
- **Rule:** SDS/7500 layouts, `AutoBaseline` true: `baseline_start`/`baseline_end` are the window (two or more cycles) whose least-squares line equals `Rn − ΔRn`, when exactly one does; otherwise none (a note counts them). `AutoBaseline` false: the setting, as before.
- In the same 240 wells the protocol's stored `Threshold` equals the export's `Ct Threshold` with `Automatic Ct` on, `Undetermined` wells are our `undetermined`, every Ct equals ours, and every `Tm1`–`Tm3` equals our `tm` list.

## 2026-09-26 — LightCycler 96: Negative calls with plausible stored Cqs; absolute-quantification analyses

**Question (reported by the RDML R package tests):** `rdml-lc96-bactxy` returns 258 of 384 reactions `undetermined` although the RDML holds a `<cq>` for them (A1 FAM 33.56, which rdmlpython reports); the rule of 2026-09-26 had been derived from absurd stored values (100, 72.55 of 50 cycles) and three files' results tables.
**Corpus files used:** `rdml-lc96-bactxy` (RDML package, MIT), `lc96p-pendo-hmuy-hm-dip`, `lc96p-pendo-hmuy-24h48h-r12`, `lc96p-pendo-hmuy-24h48h-r34`, `lc96p-pendo-hmuy-cq-xlsx` (Zenodo 14965510, CC-BY-4.0). Development tier only.
**Prior art consulted:** none (Python `zipfile`/ElementTree over the files; no public LightCycler 96 documentation of the call semantics was found).

**Evidence:**
- `rdml-lc96-bactxy` carries the software's absolute-quantification analysis (`absQuantDataModel`, not read before): 64 graphs, each with the software's `call`. The 56 Positive graphs have a `cq` equal to the RDML `cq` (21.8 to 37.97); the 8 Negative graphs have no `cq` element, although their stored RDML values are 42.08, 40.33, 40.9, 29.57, 37.88 and 100 (three times) of 50 cycles. Its replicate rows (`absQuantStatisticalRow`) give the 36 groups' Cq mean and SD, equal to the mean and SD of their members' Cqs (36 of 36); the 8 Negative graphs' rows have no Cq mean.
- The three `.lc96p` files: the depositors' table of the software's results lists exactly the Positive wells; their Negative wells hold stored numbers below the cycle count too (55 of 60 in `-r34`, 2.93 to 24.05 of 35 cycles).
- Curves: over all 384 reactions of `rdml-lc96-bactxy`, Positive calls rise a median 104 % above their baseline (cycles 4–13) by the last cycles (rise / baseline SD 103); Negative calls with a stored number below 50 rise 20 % (7.5 SD), Negative calls with 100 rise 8 %. A1 FAM (stored 33.56) rises 12 % (4 SD): not an amplification.

**Decision:** the rule stands: a stored RDML `cq` under a call other than Positive is not what the software shows, and `cq` stays null (`cq_stored` keeps the number). Changes: the `absQuantDataSource` / `absQuantStatisticalRow` rows are read like the relative-quantification ones (the analysis' Cq per graph, the groups' Cq mean and SD: `rdml-lc96-bactxy` gains `cq_mean`/`cq_sd` on 56 reactions), a graph an analysis lists with a Cq keeps it whatever the call (no corpus case), and the note says how many of the withheld values an analysis lists without a Cq. The qPCR corpus test used to count a withheld value as a matched Cq, so the 303 withheld values of `rdml-lc96-bactxy` passed unseen; it now counts them apart and fails unless the per-file count is the adjudicated one (`LC96_WITHHELD` in `crates/openreadout-corpus-tests/tests/qpcr_oracle/mod.rs`).


## 2026-10-02 — RDML: a stored `cq` at the cycle count is undetermined

**Question (website audit):** in `rdml-stepone-std` the three no-template controls (A1–A3) store `<cq>40.0</cq>` and were reported as determined Cqs; the `.eds` reader already reads the same vendor's "Ct = cycle count" as undetermined (2026-09-24).
**Corpus files used:** `rdml-stepone-std` (RDML package test data, MIT). Development tier only.
**Prior art consulted:** none beyond the committed oracle (`corpus/oracle/qpcr/rdml-stepone-std.json`, rdmlpython, MIT, run as a black box), which reports the stored number.

**Evidence:**
- The file is a StepOne export (`<instrument>` Applied Biosystems StepOne): every reaction has 40 amplification points (cycles 1–40). Its thermal program reads as 41 cycles (`loop` with `repeat` 40), so the measured curve, not the program, gives the cycle count.
- Curves: the three NTCs rise 2.6–3.3 % above their baseline (cycles 4–13) by the last three cycles; the 21 reactions with a Cq below the cycle count rise 257–331 %. A threshold crossing at exactly the last cycle is not what the NTC curves show.

**Decision:** after the LightCycler 96 calls are applied, a stored RDML `cq` ≥ the cycle count (the last cycle of the assay's amplification curve, else the run program's) is reported as undetermined, the number kept in `cq_stored`, the record flagged `cq_at_cycle_count`, and `info` notes how many. The qPCR corpus test counts these apart from matched Cqs and fails unless the per-file count is the adjudicated one (`CYCLE_COUNT_WITHHELD`: `rdml-stepone-std` 3).

**Prior art consulted:** none. `oracle/qpcr.py`'s own `export_results` (written earlier in this project for the `.eds` oracles) shows how the corpus already reads the Applied Biosystems `Results` sheet; it was not copied into the reader. The workbooks were listed cell by cell with xlrd (BSD) and openpyxl (MIT), the CSV files read as text.

**What was inferred from what:**
- Applied Biosystems: every export has a key/value header block (column A key, column B value: `Block Type`, `Chemistry`, `Experiment File Name`, `Experiment Run End Time`, `Instrument Type`, `Passive Reference`, calibration dates), a blank line, then a table whose header row starts with `Well`. StepOne Software numbers nothing and names wells `A1`; QuantStudio and ViiA 7 software number wells from 1 and add `Well Position`. The Ct column is `CT` (QuantStudio, ViiA 7) or `Cт` with a Cyrillic `т` (StepOne Software); a well without a Cq says `Undetermined`. In the three exports of runs whose `.eds` is in the corpus, every Ct equals the `.eds` result and every `Undetermined` is a well the `.eds` stores at the cycle count (already checked by `tests/qpcr_exports.rs` and the `.eds` oracles). `Block Type` (`96well`, `96-Well 0.2-mL Block`, `384-Well Block`) fixes the plate. Tables end at a blank line; below it, ΔΔCt exports add `RQ Min/Max Confidence Level` and `Reference Sample` lines. Upper-case columns (`HIGHSD`, `NOAMP`, `THOLDFAIL`, `MTP`, `EXPFAIL`, …) hold `Y`/`N`. The QuantStudio 3/5 and ViiA 7 exports add `Amplification Data` (`Well`, `Well Position` or not, `Cycle`, `Target Name`, `Rn`, `Delta Rn`; one line per well, target and cycle, 40 cycles) and `Melt Curve Raw Data` (`Reading`, `Temperature`, `Fluorescence`, `Derivative`, with or without `Target Name`).
- Bio-Rad CFX: the header row is `,Well,Fluor,Target,Content,Sample,…,Cq,…` (an empty first column); wells are `A01`; `Content` is `Unkn`, `Std-01`, `NTC`, … (the CFX well types, with a replicate number); `Cq` is `NaN` where the software found none. CFX Manager writes `N/A` for the same (HTqPCR's file, not added). The table holds no plate size.
- **Rules:** every value is taken from a column found by its header name, never by position. `Undetermined` (Applied Biosystems) and `NaN`/`N/A` (CFX) are "no Cq" (`cq_status` `undetermined`). A CFX `Content` that is not a CFX well type names no task. Detection needs the vendor's header (the Applied Biosystems header block, or the CFX column names) so that other tables with a `Well` column are not read as qPCR results.

**Validation:** `oracle/qpcr.py` `export_file` reads every export with xlrd, openpyxl or the csv module, written from the files' text and not from the reader, and the corpus test compares every result (well, target, sample, dye, task, Cq or undetermined, Tm) and the count and sums of every amplification and melt curve: 9 of 9 files agree (914 Applied Biosystems results with 36 Undetermined, 242 amplification and 242 melt curves; 192 CFX results, 27 without a Cq). On the two exports with curves our own Cq agrees with the exported Ct (median |d| 0.021 cycles, r 0.99998, on the QuantStudio 3 file; 0.153 cycles, r 0.991, on the ViiA 7 file, where 1 Ct is only the vendor's and 3 only ours).
