# Provenance log — Sciex `.wiff` + `.wiff.scan`

Rules: `docs/legal/clean-room-policy.md`. Notes for this format (in force for every entry below):

- Conversions to mzML/mzXML appear only as the depositors' own `.mzML`/`.mzXML` files, read with `pyteomics` (Apache-2.0).
- `.wiff2` files are not read at all. The clean-room policy names `.wiff2` as the known encrypted format; the reader recognises the extension and refuses it (exit 6) without inspecting the content.
- The legacy `.wiff` is an OLE2 compound file. Its container was read with our own `openreadout-core::cfb` (written from Microsoft's public [MS-CFB] specification) and, during exploration only, with `olefile` (BSD-2-Clause) to list and dump streams. The streams and the `.wiff.scan` data were derived from hex dumps and small numpy (BSD) scripts comparing the files with the depositors' conversions.

### Method and inferences

1. **Container.** Both `.wiff` files are compound files (`D0 CF 11 E0`, version 4, 4096-byte sectors). Every stream we decode starts with a 32-byte preamble (u32 0, u32 version 4 or 5, 24 zero bytes).
2. **Scan index (`SampleSubtree/Sample1/Idx`).** After the preamble, 54-byte records, one per scan (MRM file: one per cycle; TOF file: 13 per cycle, one per experiment, empty ones with length 0): u32 offset and u32 byte length of the scan's data in `.wiff.scan` (offsets relative to byte 0x2C, the end of that file's header; the last record ends exactly at the file end in both files), f64 time in milliseconds (the export's scan times × 60,000, exact), u16 (6 in every record), f64 total ion current (the export's TIC chromatogram and `total ion current`, exact), f64 base-peak intensity, f64 (0), f64 base-peak position (a TOF bin; see 6), u32 (0).
3. **MRM data (`.wiff.scan`, scheduled MRM).** Little-endian f32 values in which a negative value −(n + 0.01) stands for n zeros (every negative value in the file has the fraction .01, no zero is stored). Expanded, each cycle holds 2 × 165 values; the first 165 are zero in every cycle, the second 165 are the transitions in method order: column 165 + k equals every point of the export's chromatogram `transition=k` (165 of 165 chromatograms bit-identical in time and intensity), and each cycle's values sum to its index TIC.
4. **Method (`MethodSubtree/Method1/DeviceMethod0/Period0/ExperimentN`).** `MassRangeEx/MassRangeEx`: after the preamble, u32 2, u32 parameter count, then one record per transition / mass range: f32 (Q1 / start mass), u32, f32 (Q3), f32 (retention time in minutes in the scheduled-MRM file), u32, a u16 byte length and a UTF-16 compound name, then the named parameters (u16 byte length, UTF-16 name, f32 value, f32 value, u32): `DP`, `EP`, `CE`, `CXP` for MRM; `DP`, `CE`, `CES`, `IRD`, `IRW`, … for TOF experiments. The Q1/Q3 values equal the export's targets. The export writes collision energy 0.0 and dwell time −0.001 for every transition, while the method holds the real values (`CE` 37.9 eV …); we report the method's values and the harness ignores the export's placeholders. `ExperimentHeader`: u16 at 0x7A = scan type (4 in the MRM experiment, 8 in the TOF MS experiment, 9 in the product-ion experiments), u16 at 0x56 = polarity (1 in every experiment of the negative-mode file, 0 in the positive files), u32 at 0xB0 = number of mass ranges (165 in the MRM experiment).
5. **Scheduling.** `SampleDAM/sMRMPro_adw1/sMRMPro_adw_Times`: after the preamble, one (u32 start, u32 end) pair in milliseconds per transition; every value equals a scan time. The export's chromatogram of transition k holds exactly the scans with start ≤ t ≤ end, except that a scan at a window boundary whose whole cycle is zero (a scan written while the instrument switches the set of transitions) is left out of the transitions starting or ending there — 148 of 165 windows need no exception, the other 17 are all of that kind, and no window keeps such a scan (the first scan of the run is kept). Inferred from one file.
6. **TOF data.** Each scan is a byte stream: `FF FF FF FF` + u32 = the TDC bin of the first value; a byte 0x00–0x7B = a count (then the next step); 0x7C + u8, 0x7D + u16, 0x7E + u32 = a larger count; 0x80–0xFB = skip (byte − 0x80) empty steps; 0xFC + u8, 0xFD + u16, 0xFE + u32 = skip that many steps; one to four 0xFF bytes may end a scan. Found in stages: (a) with 1/2/3-byte operands for 0x7C–0x7E the counts of every scan summed exactly to the index TIC (the fourth operand byte of 0x7E is almost always 0 and was read as a zero count), but (b) the index's base-peak position then sat 89,769 bins (negative file) or 261,420 bins (positive file) from the decoded maximum while the decoded maximum stayed at the same bin scan after scan; a least-squares fit of that distance over 80 scans against the number of count tokens and the sum of skips before the maximum gave exactly 4 bins per token and per skipped step (residual 3e-10), i.e. one stored step is 4 TDC bins. `ExperimentHeaderEx` holds a u32 4 at 0x38 in every experiment of both TOF files and 1 in the MRM file, which we read as that grouping. (c) The alternating zero counts after every 0x7E and 0xFE token then showed that both carry a 4-byte operand (the byte after the third operand byte is 0 in 84,546 of 85,000 cases and 1–4 otherwise). With (a)–(c): the counts of all 8,372 scans sum to the index TIC, the index's base-peak position is the first maximum of the decoded profile in all 8,275 scans that store one, and for the 96 product-ion scans that store none the export's base-peak m/z is the calibrated first maximum. `SampleSubtree/Sample1/TDCInfo` holds f64 0.025 (the bin width, ns); `TOFCalibrationData` holds, after the preamble, a default (a, t₀) pair of f64, u32 0, u32 = number of index records, then one 20-byte record (f64 a, f64 t₀, u32) per index record: m/z = (a · (0.025 · bin − t₀))². With this, the index's base-peak bin gives the export's `basePeakMz` of all 956 MS1 scans of `Col-0-1_P` and the `base peak m/z` of all 8,371 spectra of the negative-mode export to 1e-9 or better (the exports print 15 digits). The export's centroids sit on the decoded peaks (86 % within one step of a non-empty step; the vendor's peak picking places the rest between steps).
7. **Precursors (`DDERealTimeData`).** After the preamble, one 32-byte slot per cycle and product-ion experiment (12 per cycle): f64 precursor m/z, f64 (0), f64 (an integer, 102–410; not interpreted), f64 (0). A slot is filled exactly when the matching product-ion record has data (11,469 of 11,472 in the positive file; three filled slots have an empty scan), and every one of the 7,290 MS/MS precursors of the negative-mode export equals its slot (to 1e-9 relative; the export prints 15 digits). The export's native ids `cycle=C experiment=E` are record ⌊i / 13⌋ + 1 and (i mod 13) + 1; the export leaves out the last, unfinished cycle (one MS1 scan), which we keep.
8. **Metadata.** `SampleSubtree/Sample1/Log` is UTF-16 text naming the mass spectrometer (`Component ID: QTRAP 6500+`, `Manufacturer`, `Model`, `Serial Number`, firmware); `SampleSubtree/Sample1/SampleDABE/DATA` holds u16-length-prefixed UTF-16 strings (sample name, sample id, comment, data file, acquisition method, …); `SampleSubtree/SampleTable` holds a u32 Unix time at 0x3E equal to the export's `startTimeStamp` (2021-09-23T16:03:25Z); `FileRec_Str` names the software (`Analyst 1.7.2`); `MethodSubtree/Method1/AcqMethodFileInfoStm` the acquisition-method path.

## 2026-09-24 — Scan headers without peaks (`spectra`, `Dataset::visit_scan_headers`)

**Scope:** the same code as a decoded spectrum with nothing read from `.wiff.scan`: level, RT, polarity, MRM precursor and collision energy, TOF product-ion precursor slot and collision energy, and for TOF scans the index record's TIC and base peak; an MRM group's TIC and base peak need its intensities and are left out. Negative-mode collision energies keep their recorded sign (−30), where exports list the magnitude.

**Validation:** `crates/openreadout-corpus-tests/tests/scans.rs` compares every oracle scan's header (scan number or native id, MS level, RT, polarity, filter, precursor m/z, charge, activation, isolation target, collision energy, 1/K0, position) with the corpus oracles (pyteomics on the depositor mzML: 1 file, 8 371 scans), and on up to 40 scans per file checks that the header equals the decoded spectrum's metadata.

**Prior art consulted:** none new.

**Harness changes** (`crates/openreadout-corpus-tests/tests/corpus.rs`): an SRM chromatogram id whose `start=` equals its `end=` carries no window (ProteoWizard copies the old dwell time there); the non-zero-point comparison also accepts times rounded to f32; a multi-sample file's first TIC/BPC trace (`TIC (sample 1)`) stands for the export's.

## 2026-09-26 — single-file `.wiff` (scans inside the compound file; held-out finding C-M2, reproduced on a development file) (Richard Zimring with Claude as assistant)

**Why:** a held-out Analyst-era `.wiff` came without `.wiff.scan`, and the reader reported the companion missing. Not investigated on that file: PRIDE was searched for projects whose `.wiff` files have no `.wiff.scan` and that carry a same-stem open-format export.
**Corpus files:** `pxd002265-qstar-xl-mmp2-gluc` (PRIDE PXD002265, EBI terms of use; QSTAR XL, Analyst QS 1.1, 2011) with the depositor's mzXML (ProteoWizard 3.0.6325). A second candidate, PXD001122's `95086EcoGU.wiff` (QSTAR, Analyst QS 1.1, 2009) with an mzWiff 4.3.1 mzXML, was examined but not added: mzWiff deisotopes and writes different times for the product-ion scans, so it is no reference for them.
**Prior art consulted:** Microsoft's public MS-CFB specification, as before; olefile (BSD) run to list and dump streams.
**Observed:** these files have `SampleSubtree/Sample1/Scan` (51–54 MB), the size of the scan data. It starts with the usual 32-byte stream preamble; right after it, and at every index record's offset from there, begins a TOF scan (`FF FF FF FF` + a TDC bin, as in `.wiff.scan` after its 44-byte header). So the index offsets count from the end of the preamble (`STREAM_PREAMBLE`) instead of from `SCAN_FILE_HEADER`, and the scans decode with the existing TOF decoder. `TOFCalibrationData` is 56 bytes (no per-scan records): the default calibration applies. `MassRange` storages hold one `MassRangeK/MassRange` stream per range (f64 masses) with the parameters in `MassRangeK/CompoundDepParams/ParameterJ/ParameterData` (UTF-16 key, f32 values); not decoded (they carry the scan window and CE only; for TOF experiments no value depends on them).
**Validation:** against the export, all 5,161 exported scans line up with ours by position (ours has one more: the last, unfinished cycle), with equal times, MS levels and precursor m/z (largest difference 5·10⁻¹³). The export labels the product-ion activation `collision-induced dissociation` where the TripleTOF exports say beam-type CID: inferred as the writer generation's convention (Analyst QS → `CID`, otherwise `HCD`); no field of the file states it.
**Decided:** without a `.wiff.scan`, the scans are read from each sample's `Scan` stream (ranges read through `Cfb::read_range`, without reading the stream whole). A file with neither still gives metadata and the index only.
**Also (same day): assurance profile.** No parsing change. The structural instrument feature is the instrument generation (`generation TripleTOF`, `generation QTRAP`, `generation QSTAR`, …) rather than the exact model string (descriptive): the scan layouts follow the generation (TOF histograms, MRM cycles), not the model within it.

## 2026-09-26 — the acquisition start is a local clock (second opinions)

**Corpus files:** `mtbls6084-sl-st-blank2`, `mtbls11360-col-0-3-n`, `pxd069939-dda-pbqc-hf75`, `pwiz-sciex-enolase` (development inputs). **Prior art consulted:** the [MS-CFB] specification (Microsoft Open Specifications, public): a directory entry's creation time (offset 0x64) and modification time (0x6C) are FILETIMEs in UTC.
**What was found.** The second-opinion harness (`oracle/second_fields/ms.py`, olefile on the storages' creation times) showed that the u32 at `SampleTable` + 0x3E, read as Unix seconds, is 8 h (`mtbls11360`), 10 h (`pxd069939`), 2 h (`mtbls6084`) and −7 h (`pwiz-sciex-enolase`) away from the compound file's own creation time, which the acquisition software writes within a second of starting the run. The offsets are whole hours and fit the depositors' locations and seasons (a September run in central Europe +2 h, a 2007 run on the US west coast −7 h), so the field is the acquisition computer's local clock stored as if it were UTC; the conversions' `startTimeStamp` values that first "confirmed" it (entry of 2026-09-24, `mtbls6084`) were themselves a local clock with a `Z` suffix. The reader reported it with a `Z`, i.e. hours off.
**Changed.** `acquired_at` (and `experiment.acquisition.started_at`) is now that local clock with the UTC offset it has from the earliest storage creation time (rounded to a quarter hour; used when it is within two minutes of a quarter-hour offset and within ±14 h), e.g. `2023-05-15T00:57:30+08:00`; without creation times it is the local clock with no zone. `openreadout_core::cfb::CfbEntry` gains `created` (the entry's creation FILETIME).

## 2026-10-06 — the precursor of a product-ion experiment that is not data-dependent (Richard Zimring with Claude as assistant)

**Corpus files used:** `mtbls851-dry-cal20180201114106110` (MetaboLights MTBLS851, TripleTOF 5600, Analyst TF 1.6, an automatic calibration run) and its depositor mzML; for comparison the data-dependent development files `mtbls11360-col-0-3-n`, `mtbls4618-t-i-128-1-hilic-neg`, `pxd069939-dda-pbqc-hf75`. **Prior art consulted:** olefile (BSD-2-Clause, https://github.com/decalage2/olefile) to list the compound file's streams; none of its code is used by the reader.

**What was found:** the calibration run has a TOF MS experiment and one TOF product-ion experiment, and no `DDERealTimeData` stream, so the reader gave its 56 MS/MS scans no precursor. The depositor's export gives 403.11219 on each, and the run's method text names 403.11219 as "the precursor mass selected for MS/MS calibration". That value is stored once in the compound file, as the f64 at offset 0x2A of the product-ion experiment's `ExperimentHeader`. In the data-dependent files, the same f64 holds small whole numbers (1.0, 2.0, … or 30.0) that are not m/z values, and their precursors come from `DDERealTimeData`.

**Decided:** in a file without `DDERealTimeData` that has exactly one TOF product-ion experiment, that experiment's precursor is the f64 at 0x2A of its `ExperimentHeader` (when it is a positive finite number). Files with several product-ion experiments and no data-dependent data (for example SWATH) are left as they were: no development file of that kind confirms what the value means there. The scans report the acquisition `fixed precursor` so the assurance profile can tell this path from the data-dependent one.

**Merged with other work (same day):** the SWATH work below reached the same reading of the f64 at 0x2A independently: without `DDERealTimeData` every TOF product-ion experiment takes it as its precursor (`extra.data_independent`). That rule covers this calibration run too, so the reader uses it, and the narrower rule above (one product-ion experiment only) was dropped when the two branches were merged.

## 2026-10-06 — scheduled MRM without stored detection windows (Richard Zimring with Claude as assistant)

**Corpus files used:** `mtbls2240-bal-214-ecoli` (MetaboLights MTBLS2240, QTRAP 6500, Analyst 1.6.2, scheduled MRM, ten samples) and its depositor mzML; for comparison `mtbls6084-sl-st-blank2` (scheduled, with `sMRMPro_adw_Times`), `mtbls3956-arg-1` and `pwiz-sciex-pressuretrace` (not scheduled). **Prior art consulted:** olefile (BSD-2-Clause) to list the streams; none of its code is used by the reader.

**What was found:** in `mtbls2240` the export's SRM chromatograms hold 101 to 162 points each, starting about 2 min before the transition's expected retention time, while the reader returned all 2,162 cycles of every transition. The file has no `sMRMPro_adw_Times` stream. Each MRM experiment has a 52-byte `sMRM` stream: the u32 at 0x24 is 1 in both scheduled files and 0 in both unscheduled ones, and the u32 at 0x28 is 240 in `mtbls2240`, 120 in `mtbls6084` and 60 in the unscheduled files. The cycle records of `mtbls2240` hold a value for every transition, so no value moves when a window is applied; outside a transition's window its values are small and the export leaves them out.

**Inferred, and decided:** the u32 at 0x24 says the experiment is scheduled, and the u32 at 0x28 is the detection window in seconds. When a sample has no stored windows and its MRM experiment is scheduled, each transition's window is its expected retention time (`MassRangeEx`) plus or minus half the detection window, and the reader returns a transition only in the cycles inside it, as it does with stored windows. The corpus test compares every SRM chromatogram of the file with the export.

**Measured against the export, and what stays open:** with these windows 72 of the 191 SRM chromatograms equal the export's and most of the others differ by one cycle at one end of the window. Placing each exported chromatogram on the run's cycle times shows its first and last points between 120.8 s before and 120.8 s after the expected time, while cycles at 120.75 s are left out of others, so Analyst does not judge the window at the cycle's time. It most likely judges it at each transition's own time within the cycle, which the file does not give us. Transitions whose expected time is 0 (eight here) are not scheduled: the export holds them over the whole run, and the reader now does too. The file is kept as a development file with `oracle_skip` naming this difference, and the layout `scheduled MRM, method windows` stays unvalidated, so `--strict` refuses these spectra.
