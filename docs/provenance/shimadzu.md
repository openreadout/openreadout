## 2026-09-24 — chromatogram and PDA samples decoded (Richard Zimring with Claude as assistant)

**Oracle:** chromConverter 0.8.x (Ethan Bass, GPL-3.0, CRAN; https://ethanbass.github.io/chromConverter/) installed into a scratch R library and **run as a black box only** (`read_chroms(format_in = "shimadzu_lcd", what = "chroms" | "peak_table")`). Its output served as known values against which layouts read off the hex dumps were tested.

**Corpus files used:** `zenodo17868549-gp070190p-hplc` (3.00, `LC Raw Data/Chromatogram Ch1`), `zenodo13987390-chiral-11a-ad` (5.01, `PDA 3D Raw Data/3D Raw Data`, `Max Plot`, `Wavelength Table`, `GUMM_Information/ShimadzuPDA.1/PDA.1.METHOD`), `zenodo13950130-std-501` (LC-MS; no UV/PDA stream; chromConverter cannot read it either).

**Inferred from hex dumps, confirmed against the oracle:**
- A 2-D signal stream (`Chromatogram ChN`, `Max Plot`): `RC\0\0`, u32 sampling interval in ms (500; 640), u32 point count (3,017; 3,752), u32 stream length, 8 bytes 0; then blocks until the count is reached: u16 `n`, `n` bytes of values, u16 `n` again. A block holds up to 256 values; its first value is absolute, the rest are differences from the previous one. A value is 1 to 8 bytes: the top three bits of its first byte are the number of further bytes; the remaining 5 + 8·k bits are a two's-complement integer (`40 58 44` = 22,596; `5F AE A6` = −20,826; `39 EF` = −1,553; `20 2F` = 47). Every one of the 3,017 values of the 3.00 file equals chromConverter's output exactly; so do all 3,752 values of the 5.01 file's `Max Plot`.
- The 3-D PDA stream is a sequence of such records, one per time point, each with the same 24-byte header (u32 1 where the interval would be, u32 wavelength count, u32 record length). 3,752 records of 491 values; the `Wavelength Table` stream holds u32 491 and 491 u32 wavelengths in 1/100 nm (189.69 … 800.33 nm). The maximum over the wavelengths of every record equals the `Max Plot` value of that time point on all 3,752 records (and chromConverter's chromatogram of this file is that max plot, in mAU = value / 1000).
- The PDA method (`PDA.1.METHOD`, UTF-16 XML with `<UPD ID="..."><Val>`) gives `SmplRt` 640 (ms) = the stored interval, `StTm` 0, `EdTm` 2,400,000 (ms), `StWav`/`EdWav` 190.00/800.00 nm, `WavStp` 1.00 nm (the stored table is ~1.23 nm apart: the diode spacing). chromConverter spreads the 3,752 points over exactly 0–40 min (step 40/3751 min); we use the stored interval (0.64 s), which ends 0.64 s later; the method's own sampling rate is the evidence.
- The 3.00 file's single channel has no unit anywhere in the file (chromConverter reports none); its values are the detector's integer output and are reported unscaled with no unit.

**Not established:** PDA values other than each scan's maximum are checked only structurally (every record decodes to its declared count and length); the vendor peak table (`LSS Data Processing/PT-PDA...`) was read by the oracle but its processing wavelength and baseline are not decoded, so it could not validate other columns. MS (TLM) raw data, `.gcd`, and chromatogram streams of other detectors than Ch1 have no corpus file.

## 2026-09-24 — Chromatogram point count, detector names and intensity scale against a vendor ASCII export (N-L1 of the second generalization report)

**Problem:** each `.lcd` chromatogram was one point short of the vendor's LabSolutions ASCII export, and traces were named after streams (`LSS Ch1`–`Ch3`) with no detector identity.

**Corpus files used** (new; none from the held-out GitHub actolonen/Analysis_Lab):
- `lcd-streamfind-adc-uv` + `lcd-streamfind-adc-uv-txt`: LCsolution 1.25, older layout (`LC Raw Data`), SPD-20AV UV detector ("Detector A", 280 nm) and an analog board ("AD1"), a 35-min run at 500 ms, and its LabSolutions ASCII export;
- examined but not added to the corpus: `karl.lcd` + `karl.txt` from the same folder, LabSolutions 5.109, newer layout (`LSS Raw Data`), an LC-40/LCMS-8060 run with status logs and a `2D Data Item` channel table, and its ASCII export. It has no LC chromatogram stream (only MS and status traces), so it has nothing for the reader's chromatogram traces to be compared with.

Both come from GitHub odea-project/streamfind at commit 69f75b6 (`bindings/r/dev/dev_reader/example_files`). The licence is GPL-3.0 (repository `LICENSE.md`, checked with the GitHub API 2026-09-24); only the data files are used. The corpus already takes GPL data files the same way (`wdf-orange-undefined-type`).

**Prior art consulted:** none.

**Observed:**
- **Point count.** The ASCII export's `[LC Chromatogram(Detector A-Ch1)]` has `# of Points` 4201, 0.000–35.000 min. The stream's header count is 4200 at 500 ms. The export's point k+1 equals our stored point k times a constant (ratio 0.0047684, p1–p99 0.004765–0.004771; residual ≤ 1 printed unit), and its point 0 repeats point 1. The same holds for every section of both exports: `AD1`, and the 6 + 10 `LC Status Trace` sections, whose `StatusLog ChN` streams use the same `RC` record (402 stored vs 403 exported points in the newer file). The vendor's chromatogram therefore starts at t = 0 with the first stored reading, and stored reading k lies at (k + 1) × interval. chromConverter (the corpus's black-box oracle) returns the stored points only, starting at t = 0.
- **Scale.** `LC Raw Data/Chromatogram Status` holds one 64-byte record per channel (channel N at (N − 1) × 64): u16 module code at +4, f64 factor at +16 (0.00476837158203125 = 10000 / 2²¹ for the SPD detectors of both older-layout files, 0.2 for the analog board), f64 1.0 at +24, f64 1000 at +32, and f32 detection wavelength at +58 (280 nm and 220 nm, matching the export's `Wavelength(nm)` 280). stored × factor is the export's `Intensity` column exactly (to its printed integer), and the export's `Intensity Multiplier` 0.001 = 1 / (f64 at +32) turns it into its `Intensity Units`, mV. The earlier note's "≈ 210 × the peak table's height units" is 1 / 0.0047684.
- **Detector names, older layout.** `LSS Configuration/LC Configuration` holds 128-byte module records: u16 module code at +0, serial at +8, firmware at +24, model at +56, and user name at +72 (`SPD-20AV`/`Detector A` with code 0x34, `AD1` with code 0x01, pumps and oven with their own codes). A chromatogram's `Chromatogram Status` code names its module. The export calls the UV detector's channel `Detector A-Ch1` and the analog board's `AD1`.
- **Detector names, newer layout.** `LSS Raw Data/2D Data Item` (XML) has one `DII` per channel: `DT` 52 for chromatograms, 48 for status logs; `CN` the channel number; `DN` the display name (`AD1`); `DETN`, `DSN` (device, `LC-40D X3`, `AD`); `CF` the factor as a little-endian f64 in hex; and `ATN`, the export's own section title (`[LC Chromatogram(AD1)]`, `[LC Status Trace(Pump A Pressure)]`). The 10 status `DII`s (CN 1–10) match the 10 `StatusLog Ch1`–`Ch10` streams.

**Inferred:**
- Every `Chromatogram ChN` trace gets the vendor's leading t = 0 point (the first reading repeated), so it has count + 1 points on an axis from 0 in steps of the interval.
- Older layout: values are stored × factor × (f64 at +24) / (f64 at +32), unit mV (the export's unit for both detector kinds seen). The name is the module's user name, with `-Ch<k>` for UV detectors (modules named `Detector …`; k counts that module's channels in stream order), which is the export's naming.
- Newer layout: the name is the text of `ATN` (else `DN`) of the chromatogram `DII` with CN = N. The factor is not applied, because no newer-layout file with chromatogram data and an export was found (`karl` has none).
- The PDA max plot keeps the stored count: no vendor export of a PDA trace was available.
- **Value prefix.** The analog board's `Chromatogram Ch5` has `0x82` before every value (`82 5f 9e 58` = −25000, then `82 00` = +0 × 255 per block). As a 5-byte value (top bits `100`) the block overran. As a one-byte prefix, the 4,200 values are −25000 each, and × 0.2 that is the export's −5000 at every point. Bytes `0x80`–`0x9F` never begin a value in the other channels (the widest values in the corpus use 4 bytes), so the reading is unambiguous there. The prefix's meaning is not known.

## 2026-09-26 — Status traces, vendor peak tables, `.gcd` and newer-layout chromatogram units (Richard Zimring with Claude as assistant)

**Why:** LC status traces (pressures, temperatures) and LabSolutions' own peak tables were not exposed; newer-layout chromatograms stayed unscaled integers; `.gcd` had no corpus file.

**Corpus files used:**
- `lcd-streamfind-adc-uv` + its ASCII export (already in the corpus): 6 `[LC Status Trace(...)]` sections and `[Peak Table(Detector A-Ch1)]` with 8 peaks.
- New: `lcd-streamfind-karl` + `lcd-streamfind-karl-txt` — `karl.lcd` and `karl.txt` from GitHub odea-project/streamfind at commit 69f75b6 (`bindings/r/dev/dev_reader/example_files`; GPL-3.0 repository licence, data files only, as for `lcd-streamfind-adc-uv`). LabSolutions 5.109, newer layout, LCMS-8060 with 10 status logs; the export holds 10 `[LC Status Trace(...)]` sections.
- New: `gcd-cct-fs19-214` — `FS19_214.gcd` from GitHub ethanbass/chromConverterExtraTests at commit 89c1ffe (`inst/`), CC0 per the repository README (depositor Andrew W. Legan). A GC run (LabSolutions 5.x, FID `SFID1`), newer layout, with its LabSolutions peak table of 83 peaks.
- Also used: the corpus's `zenodo17868549-gp070190p-hplc` (older layout, 9 vendor peaks) and `zenodo13987390-chiral-11a-ad` (newer layout, PDA, 4 PDA-channel peak tables).

**Prior art consulted:** none.

**Observed:**
- **Status logs.** `LC Raw Data/StatusLog ChN` (older) and `LSS Raw Data/StatusLog ChN` (newer) are `RC` records like the chromatograms (interval 1000 ms). `… /StatusLog Status` holds one 64-byte record per channel with the layout of `Chromatogram Status`: u16 module code at +4 (older layout; 0 in the newer), f64 at +16, +24 and +32, and the unit as text at +40 (`kgf/cm2`, `bar`, `C`, `mV`, `uV` — `Chromatogram Status` records carry it too). The export's `Intensity` column is stored × (+16) × (+24); its `Intensity Multiplier` is 1 / (+32): pressures of the older file are stored × 0.1 in kgf/cm² (multiplier 1); the newer file's in bar are stored × 0.1 / 1.0197162 (the export prints `Intensity` in kgf/cm² and multiplier 0.980665). Temperatures are stored × 0.01 °C. Every point of the 6 + 10 exported status traces is reproduced (the leading t = 0 point as for chromatograms).
- **Status names.** The newer layout names each status log in `2D Data Item` (`DT` 48, `CN` = channel, `DN`, `DSN` module model, `ATN` = the export's section title, e.g. `[LC Status Trace(Pump A Pressure)]`). The older layout stores no names; its records give the module (`LC Configuration`: `LC-20AD` pumps, `CTO-20AC` oven, `SIL-20AC` autosampler, `SPD-20AV` detector). The export names (`Pump A Pressure`, `Oven Temp.`, `Room Temp.`, `Sample Cooler Temp.`, `UV Cell Temp.`) follow the module order but are not in the file, so older-layout status traces are named by module model, quantity (from the unit) and a count.
- **Peak tables, older layout.** `LC Data Processing/Peak Table-N` (N = the chromatogram channel; tables numbered 100 and above hold no peaks in the corpus): u32 peak count, u32 0, then 280-byte records: u32 flags (0x10 on peaks the export does not mark `V`), u32 retention time in ms, f64 area, f64 height at +24, f64 baseline value at the start (+40) and end (+48), u32 start and end in ms (+56, +60), u32 A/H × 1000 (+64), f64 k′ (+208), plate number (+216), plate height (+224), tailing (+232), resolution (+240). All 8 peaks of the export agree in every one of these columns (areas and heights to the export's integer, times to the ms). `LC Data Processing Original` holds the processing as acquired; `LC Data Processing` the current one (what the export prints).
- **Peak tables, newer layout.** `LSS Data Processing/PT-<data set id>[.<channel>]`: `VER1`, u32 peak count, 12 bytes, then records of (length − 20) / count bytes (1,056 for the PDA file, 792 for the GC file) whose first 64 bytes have the older record's layout. `<data set id>` is a `2D Data Item` `DSID` (`GC.1.1.DET.1.DetCh` → the chromatogram); for the PDA (`PDA.1.1.PDA.1`) the suffix is the PDA channel: channel k ≥ 1 is record k − 1 of `LSS Data Processing/Multi Chromato Table` (u32 count, then 32-byte records from byte 24 whose u32 at +24 is the wavelength in 1/100 nm: 254, 205, 330, 500 nm — scanning every diode, the best fit of channels 1–3's peak areas is 256, 204 and 332 nm). Channel 0 (298 peaks) is not in that table and is not the max plot (its areas disagree with the max plot by factors of 2–4); its areas fit a single diode at ~192 nm, so it is reported as `PDA Ch0` without a wavelength.
- **Units, cross-checked by the vendor's own peak areas.** For every peak, the vendor area and height against our trace integrated between the vendor's start and end above the vendor's baseline values: older layout (mV traces) area = 1000 × our mV·s (µV·s) — 8/8 peaks of the export file within 1 %, 9/9 of `gp070190p` within 5 %; the GC file (stored f64 values, unit `uV` in `Chromatogram Status`) area = our µV·s with median ratio 1.00004 over 83 peaks (37 of the 40 largest within 1 %); the PDA file's 254-nm channel (mean of the three diodes within ± 2 nm) = 1000 × our mAU·s (µAU·s, the stored unit: `2D Data Item` of the PDA says `<Unit>uAU</Unit>` with factor 1) within 2 % on all 8 peaks. Heights agree to < 1 %.
- **GC chromatogram.** `LSS Raw Data/Chromatogram Ch1` of the `.gcd` is an `RC` header (interval 40 ms, count 66,255) followed by count little-endian f64 values (the stream is 24 + 8 × count bytes), not the integer blocks of the LC files; `Chromatogram Status` gives factors 1, 1, 1 and unit `uV`. Its `2D Data Item` entry has `DT` 18 (not 52) and `ATN` `[Chromatogram (Ch1)]`.

**Inferred / decided:**
- Status traces: value = stored × (+16) × (+24) / (+32) in the record's unit, with the t = 0 point; names from `2D Data Item` (newer) or `<module model> <quantity> <n>` (older). `Degassing Unit Pressure(x -1000)` channels keep that name: the display factor it states is not applied.
- Newer-layout chromatograms: scaled by their `LSS Raw Data/Chromatogram Status` record (same rule and unit text) when that record exists; the peak-area check above is the validation (no newer-layout LC chromatogram with an export exists in the corpus).
- Vendor peaks are a table (`vendor_peaks`) with the peaks of every channel: signal, retention/start/end time (min), area, height (in the chromatogram's unit × s and unit), baseline values, flags; k′, plates, plate height, tailing and resolution only for the older layout (the newer records were validated in their first 64 bytes only). PDA-channel peaks are labelled with their wavelength; no PDA channel chromatogram is produced (the vendor's bandwidth weighting is not reproduced: at 205 nm our three-diode mean is 7 % off).
- `check` compares every peak with our trace (`vendor_area_mismatch` when a peak's area differs by more than 10 % for peaks above 1 % of the largest), which re-validates the units on every file read.

Addendum (same day): `2D Data Item` entries name a trace only when their kind is unambiguous by the rules every development file follows — a chromatogram entry has a title containing `Chromatogram` (and `DT` ≠ 48), a status entry has `DT` 48 and a `Status Trace(` title. An entry that fits neither names nothing; the trace keeps its stream-based name (`LSS Ch2`, `status Ch2 temperature`). This is a tightening for right-or-refuse, not a new observation.

## 2026-09-26 — LC-MS data (`TLM Raw Data`) of LabSolutions `.lcd` files

**New development files** (all CC0-1.0, from ethanbass/chromConverterExtraTests @89c1ffe, `inst/`, whose README licence table names each file's depositor and licence; no held-out record): `lcd-tlm-mrm` (`shimadzu_tlm_mrm.lcd`, LCMS-8050-class MRM, MassIVE MSV000100356), `lcd-tlm-mrm-multi` (`shimadzu_tlm_mrm_multi.lcd`, 179 scheduled MRM events, MSV000099582), `lcd-tlm-sim` (`shimadzu_tlm_sim.lcd`, SIM and product-ion scans, MSV000095616), `lcd-tlm-scan` (`shimadzu_tlm_scan.lcd`, full scan and product-ion scans, MSV000087242), each with its ground-truth slice `*_gt.csv.gz` (scan, MS level, m/z, intensity of the first spectra, converted by the depositor of the test set with ProteoWizard msconvert, which uses the vendor's own reader).

**Prior art consulted:** none. The streams were hex-dumped and inflated with Python's zlib.

**What was inferred from what:**
- `TLM Raw Data/Retention Time`: one u32 per record, milliseconds. `TLM Raw Data/TIC Data`: one u64 per record. `TLM Raw Data/Spectrum Index`: 24-byte records `u32 size, u32 1, u32 offset, u32 0, u32 record number (1-based), u32 next number` into `TLM Raw Data/MS Raw Data`, where a record is `i32 −1, u32 decoded length, u32 packed length`, then a zlib stream of that packed length. The three counts are equal in all four files.
- An inflated record starts with `u32 retention time (ms, = the Retention Time stream), u32 cycle start time, u32 event number (1-based), u32 cycle number, u32 record index`, then `u16 acquisition code`, `u16` (1 or 2), 16 bytes of event settings, `u32` (0 or 1: 0 on events 1–21 and 1 on events 22+ of the two-polarity MRM file, so probably the polarity, but nothing says which value is which: reported as `polarity_code`, polarity `unknown`), and at +40 `u32 n`.
- Codes 15 (MRM) and 11 (SIM): `n` × (u32 Q1 × 100, u32 Q3 × 100, u32 intensity); a SIM entry has Q1 = Q3. Against the ground truth: MS level 2 for MRM and 1 for SIM, m/z = Q3/100, intensities equal, in all 200 + 400 + 10 ground-truth spectra; Q1/100 is the MRM precursor. The TIC of each record equals the sum of its intensities.
- Code 14 (product-ion scan): `u32 count, u32 precursor × 100, u32 precursor × 100, u32 first m/z × 100, u32 last m/z × 100` at +40, then `count` u32 intensities from byte 60 (count × 0.1 = last − first: a 0.1 m/z grid). The ground truth's two product-ion spectra are all zeros, on a grid of 10,601 and 11,601 points where the file has 10,620 and 11,620: nothing checks the values or the grid.
- Code 10 (full scan) has the same layout (`19,520` points from m/z 49.00 to 2001.00), and the sum of its values is the record's TIC (6,726,621 in record 0), but the ground truth's profile differs point by point at the same nominal m/z (e.g. 60,734 against 43,722 at m/z 90.8; the ground truth's sum is 7,183,184 and it has 19,501 points): msconvert applies something the file does not state (the instrument's mass calibration, by the look of a resampled profile).
- **Rule:** MRM and SIM records are spectra; full-scan and product-ion-scan spectra are refused (exit 6, with a hint to convert with msconvert). Every record's retention time, TIC, event and, for MRM and product-ion scans, precursor are listed (`spectra`, `analyze chromatogram --tic`).
