### What was inferred from what

- **Signature / version:** hex dump of every corpus file: bytes `01 A1` then UTF-16LE `Finnigan`; u32 version at offset 36 (63, 64 or 66 in the corpus).
- **Header checksum:** recomputed Adler-32 (seed 0, zlib's) over `min(len, 10 MiB)` bytes with offset 148..152 zeroed; equals the stored value on `mtbls404-Blanc04` (0x97960df7) and every other corpus file (checked by `openreadout check`).
- **Sequence row, autosampler block, file-info block, run header, instrument id:** walked with a throw-away Python script following the unfinnigan/OpenTFRaw tables; accepted only when every pointer landed on a structure whose contents were plausible (strings decode, scan counts agree, the RunHeader's own-address field equals the pointer that led to it). The autosampler block's second u32 equals the linear vial index of the vial string (`D:37` → 157 with 40 vials per tray; `A:11` → 11; `C:17` → 97) — our own observation.
- **Scan index:** entry stride derived as `(trailer_address − index_address) / scan_count`: 72 bytes in v63, 88 bytes in v66. Retention times equal the mzML `scan start time` values exactly; offsets are relative to the data-stream address.
- **Profile m/z:** `mz = A + B/f² + C/f⁴ + chunk_correction` with `f = first_frequency + bin·frequency_step` and `A, B, C` the scan event's coefficients 2, 3, 4. Bit-identical to the depositor's mzML only when evaluated as `A + B/(f·f) + C/((f·f)·(f·f))`; `B/f**2` differs in the last ulp in ~2 % of points.
- **Profile rendering by the depositor's converter (known-value injection against the mzML):** each stored chunk is emitted with 4 zero-intensity bins on either side; bins `1..=4` and `nbins−3..=nbins` of the grid are always emitted as zeros; a padding bin takes the correction of the *next* chunk (the first chunk's for the leading edge, the last chunk's for the trailing edge); chunks whose m/z span contains a centroid flagged with bit `0x10` in its descriptor are emitted with zero intensity. With these rules all 2031 profile scans of `mtbls404-Blanc04` reproduce the mzML arrays bit for bit (m/z as f64, intensity as f32).
- **Filter strings are not stored in the file:** no UTF-16 or ASCII occurrence of `Full ms` exists in any corpus file; they are composed from scan-event bytes (see `docs/formats/thermo-raw.md`).

## 2026-09-22 (later the same day) — versions 64 and 66, centroids, validation

**Corpus files used:** all eleven above. No new prior art consulted.

- **Scan index row length** by version measured as (event-stream address − index address) / scans: 72 (v63), 80 (v64), 88 (v66). The OpenTFRaw figures (76/84/92) did not fit any corpus file.
- **Run-header size in v64/v66** (7576 bytes): the instrument id's first u32 (1) follows exactly 24 zero u32 after the 64-bit address block in all v64/v66 files.
- **Filter m/z decimals** (`display_words[1]`, run header offset 7404): 4 in the two Q Exactive HF files whose depositor filters print `[70.0000-1000.0000]` and `732.0000@hcd15.00`, 2 in the other nine files. Preamble byte 104 was the first candidate and was rejected because the imaging file prints 4 decimals with byte 104 = 0.
- **Scan-event layout in v66** (136-byte preamble): reaction count, reactions, three f64, one u32, range, coefficient count, coefficients, counted 8-byte items, two u32 — found by aligning the doubles 535.0/930.0 (centre/width of a 70–1000 isolation) and 70.0/1000.0 in the hex dump of the first MS1 event of `mtbls755-hilic-dpoly`, and confirmed by the stream ending exactly at the scan-parameter address in all three v66 files. The OpenTFRaw description of separate MS1/MS2 layouts was not needed: MS1 events carry one full-range "reaction".
- **Counted tail items:** the v64 Exactive file's events are 16 bytes longer than the v64 Velos file's; a u32 count (1 vs 0) followed by 8 bytes per item explains both and the v66 tail, again checked by the exact stream end in every file.
- **Activation is in the reaction record, not the preamble:** PXD000001's HCD MS2 events and MTBLS20's CID MS2 events have identical preambles except the ion source byte; their `reaction_words[0]` is 11 vs 1, and 11 in every HCD event of MTBLS755/MTBLS805. Byte 24 (4 in v63/v64, 1 in v66) does not follow the activation.
- **`{1,1}` and `lock` filter tokens:** only in `mtbls797-dotsha05` (`FTMS {1,1}  + p ESI Full lock ms [150.00-1500.00]`, two spaces after the braces). Preamble bytes 28 and 30 are 1 and 1 there and 0xFF in every other file; byte 42 is 0 there and 2 elsewhere. Both attributions rest on this single file.
- **Excluded peaks:** descriptor flag bit 0x20 marks the 445.12 lock-mass peak in PXD000001 (its method file name contains `_LM_`), which the depositor's export blanks in profiles like the 0x10-flagged peaks of MTBLS404 and leaves out of centroid lists (MTBLS20 negative mode: exactly the 0x10-flagged centroids are missing from the depositor's centroid list).
- **Centroid records:** every corpus file uses the 8-byte (f32 m/z) form; the depositors' 64-bit mzML m/z arrays hold exactly these f32 values widened.
- **Monoisotopic precursor:** the per-scan parameter `Monoisotopic M/Z:` replaces the reaction's precursor m/z when non-zero; with that rule every MS2 selected-ion m/z of PXD000001 (non-zero values) and MTBLS755/805/20 (zero values → reaction m/z) matches.
- **Known residual difference:** 371 profile scans of MTBLS755 and 25 of PXD000001 differ from the export by a constant relative m/z factor ≤ 3·10⁻¹¹; for a sample of them the export's m/z are reproduced exactly with the stored coefficients of an earlier scan of the same polarity (e.g. scan 121 with scan 106's). Tolerant event de-duplication (relative tolerances 1e-12…1e-8) and keying by 8–13 significant digits reproduce at most 1288 of 1420 profile scans, so the rule stays unknown and we keep each scan's own coefficients.
- **Monotonic m/z:** 115 MTBLS755 profile scans differed in exactly one padding bin: when a padding bin's m/z (with the next chunk's correction) falls at or below its predecessor's, the export places it at predecessor + 1·10⁻⁵ (e.g. scan 1568: 384.12713361169637 → 384.12714361169634). With that rule those scans are bit-exact.
- **mzXML retention times** are printed with limited digits (`PT1000.58S`); the oracle records half a unit of the last printed digit per scan and the harness allows it.

- **Embedded instrument method:** the byte layout in front of the compound file (header, size, temporary path, device name pairs) was read off the hex dump of `mtbls404-Blanc04` and checked on every file with `method_file_present = 1` (the declared size ends exactly at the scan-data address). The compound file itself follows the public Microsoft specification [MS-CFB] (https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-cfb/, Microsoft Open Specification Promise); `olefile` (BSD-2-Clause, a generic compound-file reader, not a vendor tool) was run once to list the streams while exploring. Our reader was written from the specification.

**Validation (corpus harness, `cargo test -p openreadout-corpus-tests --features corpus`):** 20,639 scans compared across the eleven files; peak arrays bit-exact for 20,358, within 3·10⁻¹¹ relative m/z (identical intensities) for 281 (256 in MTBLS755, 25 in PXD000001); zero metadata mismatches (scan number, MS level, polarity, profile/centroid, retention time, filter text where the export has one, precursor m/z, charge, activation).
