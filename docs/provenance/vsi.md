**Method, ETS (hex dumps, a 40-line Python walker in the session scratchpad):**
- Every `frame_t*.ets` starts with `SIS\0`, u32 64 (header size), u32 3, u32 n (4 or 6), u64 64 (offset of a second header), u32 228 (its size), u32 0, u64 T (an offset near the end), u32 N, u32 0, then u64 and u32 words we do not interpret. From offset 64: `ETS\0`, u32 `0x00030006`, then words: 2 or 4, 1 or 3, 1 or 4, 0/2/3, 90 or 100, tile width, tile height, 1, …; at +108 a value that is `0x00FFFFFF`/`0x00EEEEEE` in RGB files and `0xFFFF`/`0x0FFF` in 16-bit files; at +184 a count k followed by k sizes.
- At T there are exactly N entries of `4 + 4·n + 16` bytes (44 for n = 6, 36 for n = 4: checked by T + N·size = end of file in every file): u32 equal to n, n u32 coordinates, u64 offset, u32 length, u32 (a permutation of 0..N−1). Offsets + lengths land inside the file and the first one is right after the second header (292 = 64 + 228).
- The data at the offsets: `FF D8 FF E0 … JFIF` (JPEG) where the header word at +20 is 2; `FF 4F FF 51` (JPEG 2000 codestream) where it is 3; raw little-endian samples where it is 0, with length = tile width × height × 2 when the word at +8 is 4 and × 3 bytes when it is 2 with 3 samples. Hence +8 = sample type (2 → 8-bit, 4 → 16-bit), +12 = samples per pixel, +20 = compression, +24 = quality.
- Coordinates: the first two are tile column/row; the last one takes values 0..L−1 with tile counts shrinking about 4× per step (4414, 1178, 331, … 1 in `he-bone` stack10002): pyramid level. The ones in between (n − 3 of them) index the non-XY dimensions; their sizes are the header's size list after X and Y (e.g. `[1645, 1682, 1, 11, 2]` in the JPEG 2000 file, matching its README's Z = 11, C = 2). In RGB files n = 4 and the size list is only X, Y: the one extra coordinate is always 0.
- Level-0 image size = the first two sizes (`he-bone` stack10002: 79372 × 42232 with 512-px tiles: 156 × 83 tiles needed, only 4414 present, the top rows absent — whole-slide scanners do not store empty background tiles). Level L size = ceil(level L−1 size / 2), which reproduces every resolution size Bio-Formats reports (e.g. 8021 → 4011 → 2006 → 1003 → 502 → 251).
- Missing tiles: filled with the +108 value (interpreted as the background colour: `0xEEEEEE` light grey for the slides; not corroborated beyond the match with Bio-Formats' planes, see validation).

**Method, .vsi (hex dumps + differential comparison between the 6 files and with Bio-Formats' reported values):**
- A little-endian TIFF: header `II*\0` + offset of one IFD holding the JPEG preview (tifffile). Between the header and the preview, at offset 8, a tree of tagged records starts with the bytes `18 00 49 53` ("IS").
- A record set ("volume"): u16 24, `IS`, u32 (0x192 or 1), u32 offset of the first record relative to the volume start (0 = empty), u32 0, u32 record count, u32 0. A record: u32 type, u32 tag, u32 offset of the next record relative to the volume start (0 = last), u32 size. Walking the `next` chain visits exactly `count` records in every volume of every corpus file (6707 records in `he-bone`, no mismatch).
- Type bits (inferred from all records): `0x08000000` → a u32 index follows the 16-byte record header (repeated tags such as stacks carry their id there); `0x80000000` → a nested volume follows; `0x40000000` → no payload, the size word is the value; otherwise `size` bytes of payload follow. Low 12 bits = value kind: 0x1 bytes/UTF-8 (an embedded XML document), 0x2 bytes, 0x4 u16, 0x5 i32, 0x6 u32, 0x7 i64, 0xA f64, 0xC boolean, 0xD UTF-16 string, 0x103 4 × i32, 0x104/0x10C/0x117 2 × f64, 0x10E 256 × RGB; bit 0x2000 = array (0x2000/0x2002 UTF-16 text, 0x2003 i32 array, 0x2008 i32 box). One record kind (0x1800000A, tag 2016, the preview TIFF payload) has a size word 48 bytes larger than the space before the next record; we trust the chain.
- Values found by searching for known numbers and strings: tag 2000 → per-file volume; its tag-2001 records carry the stack id in the index (1, 10000, 10002, 10005 = directory names `stack1`, `stack10000`, … under `_<name>_/`); inside a stack: 2003 = i32 array of the non-XY dimension sizes (`[5, 18, 2]`, `[1, 11, 2]`, `[]` for RGB slides), 2034 = background bytes, 2005 → 2030 = stack name (`Label`, `Overview`, `20x_BF_01`, `488/640_50um_1x`), 2019 = pixel size x, y and 2020 = its unit string `10^-6m^1` (µm) (2.7381 µm for the label, as Bio-Formats), 2015 = i64 Unix time (1707483058 = 2024-02-09T12:50:58Z, Bio-Formats' acquisition date), 2018 = stage x, y. 2007[k] = dimension k of 2003: 2008[i] records inside it, 2023 = dimension kind (1 for the 18- and 11- and 41-deep dimensions → Z; 2 for the 5-long dimension of the time-lapse test file → T; 4 for the dimension whose entries carry channel names → C), Z step = 2013's value (0.2 µm, Bio-Formats' Z pixel size; −0.4 in the deconvolution files, we take the absolute value), channel entries 2008[i]: 2021 = name (`Cy5`, `C405`), 2417 = value in nm equal to Bio-Formats' emission wavelength (670, 508, 455, 518), 2474 = a second value in nm (625, 470) we report as excitation (**inferred**, plausible LED lines, not corroborated). 2002[k] records (one per plane, k = 0..N−1) hold a value with unit `10^-3s^1` (ms): 254.279, 15254.279, … (per-plane time). Per-device settings under 2005/2043/*: the record holding 120060 (20.0), 120061 (0.8), 120063 (`UPLXAPO`), 120062 (600 µm) matches Bio-Formats' objective (magnification, NA, model, working distance). File level: 2004/2109/34 = software (`OLYMPUS VS200 ASW`, `OLYMPUS cellSens Dimension`), /35 = its version.
- Value containers with tags ≥ 0x10000000 hold a unit string (0x10000000), a value (0x10000002) and a type word (0x10000003).

**Inferred, not corroborated:** dimension kind codes other than 1, 2 and 4; ETS sample-type codes other than 2 and 4 and compression codes other than 0, 2 and 3; the meaning of 2474 (excitation); the +108 background value as the fill for missing tiles; which ETS file to use when a stack directory holds several `frame_t_*.ets`; `blob_*` ETS files (focus-map data) — listed, not decoded.

**Validation (2026-09-22, same session, after merging origin/main).** Oracle: Bio-Formats 8.5.0 (`showinf -noflat -omexml`, `bfconvert -series`, run from `oracle/bftools`; its non-thumbnail series = our images, its thumbnail series = our `preview` attachment). Corpus harness (release): all 6 datasets pass. Fluorescence: 168 planes compared, 149 bit-identical (raw tiles: `metadatatest-01` 64/64 with T = 5, Z = 18, C = 2; both deconvolution files 41/41), the 19 remaining JPEG 2000 planes of `vsi-ets-test-jpg2k` within 3 levels of Bio-Formats (our pure-Rust decoder and OpenJPEG also differ by up to 3; 3 planes are bit-identical). Whole slides (JPEG tiles, planes over 120 MB not converted by the oracle): 35 pyramid-level planes (`he-bone` 20 over 4 stacks, `vs200` 15 over 3 stacks) within 4 levels, with identical level sizes (the clipping of each level to its stored tiles reproduces all 35 of Bio-Formats' resolution sizes) and identical background-filled areas. Physical sizes, Z step, channel names and emission wavelengths, stack names, acquisition dates and objectives agree with Bio-Formats' OME-XML. `check` reports no errors on any corpus dataset; a copy with its ETS truncated reports `truncated` and `missing_planes` (exit 4) and plane reads fail with `corrupt_file`; a `.vsi` without its `_<name>_` directory opens metadata-only and `check` reports `missing_ets_directory` (exit 4).

## 2026-09-22 — robustness (fuzzing)

**Scope:** bounds only; what the reader infers is unchanged. The `whole_vsi` fuzz target (3 min; seeds cut from `vsi-ets-test-jpg2k`, CC-BY-4.0) found: the C x Z x T plane count, a product of sizes declared in the ETS header, overflowing `u32`; `check` visiting every declared plane (2^32 in a 54 KB input: a timeout) to find planes without tiles; tile coordinates + 1 and columns x tile width overflowing; and a tile claiming pyramid level 2^32 - 1 making `level_sizes` build billions of levels. Sizes now saturate, `check` counts the planes that have level-0 tiles and subtracts, and at most 33 pyramid levels exist (a `u32` size halves to 1 by then). Fixtures: `crates/openreadout-vsi/tests/fixtures/malformed/bundle-whole_vsi-*.bin`. **Prior art consulted:** none.

## 2026-09-22 — robustness (fuzzing): bounded JPEG frames

**Scope:** a bound only. The `codec_jpeg` fuzz target found that `jpeg-decoder` sizes its per-component planes from the frame header before applying its output cap (a 342-byte stream made it allocate 4 GB), and that a tiny stream declaring about 60000 x 15000 pixels takes tens of seconds to decode. JPEG ETS tiles are now decoded with `openreadout_codecs::jpeg_decode_limited`: a frame whose decoded size exceeds four times the tile size (at least 1 MiB) is refused before decoding. Decoded pixels are unchanged. **Prior art consulted:** none.

## 2026-09-23 — Region reads (Richard Zimring with Claude as assistant)

**Scope.** `Dataset::read_region` on ETS stacks: only the tiles of the requested level whose grid cell (`column × tile_width`, `row × tile_height`) overlaps the rectangle are read and decoded (in parallel), pasted over the background colour exactly as for whole planes. Level-0 planes of whole-slide scans above 4 GiB (e.g. `40x_BF_01` of `zenodo17453126-he-bone`, 158 745 × 84 465 RGB) become readable by region. No new interpretation of the file.

**Oracle:** Bio-Formats 8.5.0 `bfconvert -crop` (GPL, run as a black box only) of the same rectangle and resolution.

## 2026-09-24 — Pyramid downsampling factors are powers of two

**Problem.** `images[].resolution_levels[].downsample_x/y` were the ratio of level-0 to level-L size. Where a level is clipped to the tiles stored at it (slides leave empty margins out), that ratio is not the level's scale: image 3 of `zenodo17453126-he-bone-vsi` (158 745 × 84 465) reported 16.106 × 16.497 for level 4 (9856 × 5120), so `level coordinate × factor` missed the level-0 position by up to 1 000 pixels.

**Corpus files used:** `zenodo17453126-he-bone-vsi`, `zenodo8161864-vs200-he-20x` (levels read through our reader, whose level-0 and level pixels match Bio-Formats 8.5.0 run as a black box: `corpus/oracle/regions/`).

**Inferred.** Level L is level L − 1 halved (the tile grid and the level sizes already say so: 158 745 → 78 848 = 77 tiles of 1024, 39 424, …), so its factor is 2^L on both axes. Checked by correlation: 16 × 16-pixel windows of level 4 at 10 %–90 % of its width correlate r = 0.97–0.99 with the block-averaged level-0 window at `position × 16`, and r = −0.07–0.13 at `position × 16.106` (`crates/openreadout-corpus-tests/tests/pyramids.rs` does this for every pyramid in the corpus). Sizes are unchanged.

**Prior art consulted:** none.

## 2026-09-24 — plane-size overflow

**Scope:** a bound only. The `whole_vsi` fuzz target (90 s, after the merge that brought exact power-of-two level factors; seeds cut from `vsi-ets-test-jpg2k`, CC-BY-4.0) found a level size near 2^32 × 2^32 whose width × height × bytes per pixel overflowed `u64` in the whole-plane size check of `read_level_region` (a panic with overflow checks; in release builds a wrapped size that `plane_bytes_checked` then refused). The product now saturates, so the plane is refused with the hint to read a region or a level. Regression fixture: `crates/openreadout-vsi/tests/fixtures/malformed/bundle-whole_vsi-plane-size-overflow.bin`, replayed as a directory by `crates/openreadout-cli/tests/fuzz_regressions.rs`.

## 2026-09-25 — Image size from the .vsi, signed tile indices, tile-grid origin; four software generations (Richard Zimring with Claude as assistant)

**Why.** Three new public datasets from other depositors and software generations were read silently wrong: the VS120 `dotSlide 2.5` files (ETS version `0x00030003`) have an empty size list in the ETS header, so the level-0 size fell back to the tile grid (31744 × 20992 instead of 31740 × 20970; 8192 × 16896 instead of 7685 × 16421); the OLYMPUS Stream Essentials 1.7 stitch (`MIA`) indexes tiles with negative columns and rows (read as 4 294 967 295 × 4 294 967 295); and the cellSens Dimension 1.18 slide places its tile grid 42 pixels left and 1 pixel above the image corner, so every pixel came out 42 columns and 1 row off.

**Corpus files used** (all in `corpus/manifest.toml`, all CC-BY-4.0; ETS files placed in the stack directory whose image size matches their tile grid, see the manifest notes):
- `figshare31724575-vsi-timelapse` (+ ETS): cellSens Dimension 3.2, 200 time points × 3 channels, 8-bit grey JPEG, one tile per plane (Chris Tiessen).
- `figshare30384007-vsi-spleen` (+ ETS, + the depositor's full-resolution PNG export `MBF_EXP_spleen_prussian_717.png`, role `oracle-export`): cellSens Dimension 1.18, ETS version `0x00030005`, RGB JPEG tiles (Konstantinos Ioannidis).
- `figshare28409411-vsi-dotslide`, `-dotslide-overview` (+ ETS): VS120 dotSlide 2.5, ETS version `0x00030003`, RGB JPEG tiles, 7-level pyramids (Christopher Brown).
- `figshare27677802-vsi-stitch` (+ ETS, + the depositor's JPEG export `stitch.jpg`, role `oracle-export`): OLYMPUS Stream Essentials 1.7, 8-bit grey raw tiles with negative grid indices (Muhammed Salojee).
- The six earlier datasets (entry of 2026-09-22) for the cross-checks below.

**Prior art consulted:** none. Bio-Formats 8.5.0 `showinf`/`bfconvert` was run as a black box (GPL) and its planes kept as sidecars (`ORACLE_SIDECARS=1`) for the comparisons below.

**Method and inferences (hex dumps of our own `info --view full` output, differential comparison, three independent references):**
- The first per-plane record `2002[0]` of every pixel stack holds a record set `2018` ("layout", our name) with `2053` = i32 `[x, y, width, height]`, `20025` = i32 `[origin per dimension…, size per dimension…]` and `2410` = one signed 32-bit value per dimension (type `0x2007`: 20 bytes for 5 dimensions, 16 for 4, 12 for 3, 8 for 2 — 4-byte elements, not the 8-byte integers of scalar kind 7). In the 10 files that store a size list in the ETS header, `2053`'s width and height equal it exactly (18 stacks). In the two dotSlide files, whose ETS header has none, `2053` = 31740 × 20970 and 7685 × 16421: Bio-Formats reports these sizes, and their level-0 tile grids (62 × 41 and 16 × 33 tiles of 512) are the smallest that cover them.
- Tile-table coordinates are signed 32-bit numbers: the Stream stitch stores columns −27…4 and rows −5…3 at level 0 (`0xFFFFFFE5` = −27). `2410` there is (13306, 2464, 0); all other files hold zeros except the spleen slide, (−42, −1, 0, 0).
- Placement rule (inferred): tile (column, row) of level 0 covers image pixels starting at (column × tile width + `2410`[0], row × tile height + `2410`[1]). Evidence: (a) spleen: the level-0 plane assembled with (−42, −1) is identical to Bio-Formats' plane (mean |Δ| 0.0), and against the depositor's own PNG export (made by cellSens, independent of Bio-Formats) it has the lowest mean difference of the five candidate offsets tried (15.14 at (−42, −1); 16.03 at (−42, 0) and (−42, −2); 16.54 at (−41, −1) and (−43, −1); the PNG carries a display transform, hence the floor of ~15); (b) stitch: with (13306, 2464)… read as the image position of tile (0, 0) = (−13306, −2464) in grid pixels, i.e. the offset added to column × width is +13306 — the assembled plane correlates r = 0.97 with the depositor's JPEG export and the mean difference is lowest (2.33) at zero shift among the 25 one- and two-pixel shifts tried (≥ 3.76 elsewhere).
- Pyramid levels: level L is placed with the offset divided by 2^L. Bio-Formats rounds that toward zero (its level planes of the spleen slide match exactly with truncation, not with floor); comparing each level with the block-averaged level 0 favours round-to-nearest where they differ (level 4 of the spleen slide: −42/16 = −2.625 → mean |Δ| 7.77 at −3, 10.21 at Bio-Formats' −2; the other levels tie). We round to nearest, halves toward zero, so our level 4 of that slide is one pixel left of Bio-Formats'.
- **Bio-Formats 8.5.0 is wrong on the Stream stitch** (black box observation, reported here rather than fixed): its level 0 is mostly zeros with a few tiles placed at the right edge, and its levels 1–5 are clipped to the non-negative tiles (1536 × 1024 for a 7693 × 2003 level). The oracle for `figshare27677802-vsi-stitch` therefore keeps Bio-Formats' level-0 geometry and physical size but not its planes; the pixels are checked against the depositor's export instead (`crates/openreadout-corpus-tests/tests/vsi_exports.rs`).

**Rules implemented:** level-0 size = ETS header size list when present (a `.vsi` rectangle that disagrees is a `dimension_mismatch` warning), else `2053` of the `.vsi`, else (standalone ETS without a size list) the extent of the stored level-0 tiles, flagged in `extra.size_source` and a note; tile placement adds the `2410` offset (rounded per level as above) to column × tile width; a standalone ETS whose tiles have negative indices is placed from its smallest column and row (the `.vsi` offset is not known).

**Inferred (differential comparison of `info --view full` output with Bio-Formats' OME-XML values):**

- The camera device's value set holds 100002 = exposure in µs (4997 and 15001 in the time-lapse's channel entries = Bio-Formats' per-plane ExposureTime 0.004997 s and 0.015001 s; 100100 holds the same in ns). Each channel entry 2008[i] has its own device set, so exposure is per channel; stacks without a channel dimension carry it in the stack settings.
- The objective device's 120079 is the immersion refractive index (1.518 for the 100×/1.45 oil lens = Bio-Formats' ObjectiveSettings RefractiveIndex; 1.0003 for dry 20× lenses).
- Settings 2419 = the name of the illumination setting: `BF` and `Label Scan` in the slide stacks, which Bio-Formats reports as their channel name; in channel entries it repeats the channel name. Used as the channel name of stacks without a channel dimension.
- Record 2037 of the first plane record repeats 2053/20025 without 2410; in one cellSens 3.2 file (`MR3777L#190_ 4x.vsi`) it is the only layout set, so the rectangle is read from 2018, else 2037.
- Dimension kinds across all 27 files: only 1, 2 and 4 occur (31 dimensions with entries); trailing dimension records without entries are empty.
- Channel emission (2417) and excitation (2474) across 9 channels in 6 files: (670, 625) Cy5, (508, 470) GFP, (455, 345) DAPI-like, (518, 494) eGFP-like, (480, 480), (670, 625): 2474 is consistent with the excitation line in every case; Bio-Formats reports only emission.
- **Bio-Formats differs:** in `ome-cellsens-metadatatest-01` it names both channels after the stack (`488/640_50um_1x`); the channel entries' 2021 records hold `Cy5` and `GFP Wild Type, non-UV excitation`, which we report.
