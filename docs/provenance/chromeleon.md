# Provenance log — Thermo Scientific Chromeleon 7 archives (`.cmbx`)

Rules: `docs/legal/clean-room-policy.md`. Each entry: date, who, corpus files, prior art (URL + license), what was inferred.

## 2026-09-26 — initial derivation (Richard Zimring with Claude as assistant)

**Order of work.** The archives were listed (`unzip -l`, Python `zipfile`), `header.xml` read as text, the members dumped with `xxd` and walked with small Python scripts written for this purpose; the hypotheses below were written down and then checked against the depositors' own vendor exports (a Chromeleon PDF report and Chromeleon ASCII chromatogram exports).

**Prior art.** None was found: no permissively licensed reader of `.cmbx` archives exists that we know of.

**Inferred from the files:**
- A `.cmbx` is a zip (deflated members). `header.xml` (UTF-8 with BOM) has the root `ChromeleonHeader` (`GeneratorVersion` = the Chromeleon build, `ContainerVersion` `2.0`, `ContainerVersionChromeleon` `7.2.3`, `DateCreated` in the exporting computer's local wording, `ItemCount`) and nested `ChromeleonElement`s with `Id`, `Name`, `Url` (`chrom://<host>/<data vault>/…`), `ItemType` (`Dionex.Chromeleon.Data.Sequence`, `.Injection`, `.Signal`, `.AuditTrail`, `.MSRawItem`, `.InstrumentMethod`, `.ProcessingMethod`, `.ReportDefinition`, `.DataPresentationLayout`), `Filename` (the sequence's `.cmd` member), `RawDataFilename` (the member of a signal, audit trail or MS item), `Size`, `RawDataFileId` (`2025\11\16\164901056.raw`) and, on injections, `InjectionType`. Signals and audit trails are children of their injection; methods are children of the sequence.
- **Signal members.** A run of sections, each an 8-byte ASCII tag and a little-endian u64 length that counts the tag and itself. `SignHdr\0` (first, 55 or 54–65 bytes): `01 02 07`, two bytes (`02 0a` in 7.2.x files, `03 01` in 7.3.1), a Windows FILETIME, `02`, a length byte and the signal name (UTF-8, equal to the item's `Name`), 16 bytes (a GUID), and a short tail of unknown meaning. `PtsLDiff` blocks follow, about one minute of data each: an f64 start time in minutes, then integers in a variable-length encoding: the first byte holds a continuation bit (0x80), the sign (0x40) and the six lowest bits of the magnitude; each continuation byte adds seven bits. The first four integers are a version (always 1), the points per minute (3000 for the GC files, 120 for the detector and 960 for the pump pressure of the ICS files), and a scale numerator and denominator (230584300921369 / 2^61 = 1.0·10⁻⁴; 230584304357343 / 2^62 = 5.0000000745·10⁻⁵, the single-precision value of 5·10⁻⁵; 510306194820673 / 2^61 = 2.2131·10⁻⁴). Then the data: the block's first value absolute, each later one the difference from the one before; a final 0 ends every block (1127 + 1126 + 1059 + 22,000 + 8,409 + … blocks, no exception). Value = sum × numerator / denominator. Each block starts exactly one sample period after the previous block's last point (no gaps in any corpus file). A first hypothesis, second differences, failed: summing twice makes the blocks discontinuous, while summing once makes each block's first value continue the previous block (e.g. 142,435,200 → 142,452,800 across a solvent peak).
- **FILETIME.** The SignHdr FILETIME is the signal's acquisition start in UTC: `2025-11-16 15:24:13.10 UTC` for an injection the PDF report lists at `16/Nov/25 16:24:12` (Germany, UTC+1); `2024-07-05 09:38:21.80 UTC` for an ASCII export's `Inject Time 5/07/2024 7:38:21 PM +10:00`. The `RawDataFileId` names the local start time (`2024\07\05\193821815.raw`).
- **Sequence file (`.cmd`).** A protocol-buffers stream (keys and lengths as varints; wire types 0, 1, 2, 5): top-level field 18 records name object types (`Sequence`, `Injection`, `Signal`, `Chromatogram`, `AuditTrail`, `ProcessingMethod`), field 19 records hold the objects, fields 20–23 relations and users, and gzip blobs appear inside some objects. A field-19 record whose first field (5) holds a message with field 6 = a `RawDataFileId` describes that signal in its field 3: 3 = an XML string `<CmData><HoldPeriods /><StepMin value=…/><StepMax value=…/></CmData>` (the step in minutes), 4 = the number of points, 5 = the time axis (1 = first time, 2 = last time as f64; 3 = unit `min`; 4 = `Time`), 6 = the signal axis (1 = minimum, 2 = maximum; 3 = unit `mV`, `nC`, `psi`; 4 = quantity, empty or `Pressure`), 11 = device (`GC`, `Pump_1`; for the ICS detector a non-text value), 12 = module or driver (`Thermo Scientific Trace GC`, `DC-6000`, `ICS-6000 SP`), 14 = a number of unknown meaning, 15 = the scale factor as f64 (0.0001, 5.0000000745·10⁻⁵, 2.2131·10⁻⁴: equal to the block header's numerator/denominator). Field 28 of the enclosing record is the signal name.
- **Consistency.** For every signal of the six archives with 2D data (553 signals including the 8 calibration standards; 1 unreadable member) the decoded point count, first time, last time, scale, minimum and maximum equal the sequence file's description (relative difference below 10⁻⁹; in fact 0), and every injection's SignHdr start is a whole number of quarter hours (the time zone) from its file id's local time.
- **MS data.** The baobab archive's `MSRawItem` member starts `01 A1` followed by UTF-16 `Finnigan`: a Thermo `.raw` file, which the thermo-raw reader handles once extracted.
- **Calibration standards.** In the 2022 archive (`cmbx-lim-tsoye-48h`) the processing method item holds `FixedInjectionList/FixedInjection` elements (`FixedInjectionName` = a standard, e.g. `Cyclohexenone 1mM with Dodecane`), each with a `Signal` item and member: 8 signals from other sequences. Their `RawDataFileId`s are consecutive (`2022\08\19\185350655.raw`, `…665`, `…675`: the time they were copied), while their SignHdr starts are in July 2022 (their acquisition), so for them the file id is not an acquisition time; `check` compares start times only for injections' signals.
- The audit-trail members start `CpAu` followed by what looks like compressed or encrypted bytes; not decoded.

**Validation against the vendor's own outputs:**
- ASCII exports (Figshare 28560326): the six exports match six injections of the archive (by injection name and, where names repeat, by start time). All 55,446 exported points agree: every time within 3.4·10⁻⁷ min and every value within 5·10⁻⁷ nC of our decode (the exports print 6 decimals); point counts (9,241) and first times (0.000167–0.0005 min) equal.
- PDF report (Zenodo 18089202): the 57 report pages are in injection order and name the same injections. On every page, the plotted chromatogram (a path of 176–1,585 vertices, x from 75.6 to 542.16 pt for 0 to 19.4 min) was compared with our decoded values of the samples in each vertex's pixel column, after a robust linear fit of the y axis (the axis labels are images): 19,367 of 19,374 unclipped vertices (99.96 %) lie within the column's range. Nineteen integrated peaks are listed; for 17 of them the apex of our trace between the drawn limits lies within one sample (0.02 s) of the printed retention time (the other two ride on a larger neighbour). The report draws each peak's baseline (a red segment) and limits (blue ticks, ±0.6 pt ≈ ±0.025 min); searching sample-exact limits within ±1 pt of the drawn ones, 6 peaks' printed height (to 0.001 mV) and area (to 0.001 mV·min, trapezoids above the straight baseline) are both reproduced to within half a printed unit, 16 of 19 within 5 % (the three riders are not: their limits are not resolved by the drawing). This confirms the time axis, the scale (value in mV) and the decode.

## 2026-09-26 — compressed blobs, Chromeleon's own integration results, injection details, components, audit trails (Richard Zimring with Claude as assistant)

**Order of work.** The sequence files (`.cmd`) of the six development archives were walked with a small protocol-buffers dumper written for this purpose (keys, wire types, nested messages) and the byte runs that did not parse as messages were hex-dumped; hypotheses were written down and then checked (a) against the depositors' vendor outputs (the Chromeleon 7.2.10 PDF report of `cmbx-lauterbach-invivo-cascade`; the six Chromeleon ASCII exports of `cmbx-figshare-milks-sugars`) and (b) by recomputing every stored peak from our own decoded signal.

**Prior art.** The compression inside the blobs is LZMA2 (public-domain LZMA SDK specification; the LZMA2 chunk layout as documented with xz, public domain): our decoder is `crates/openreadout-codecs/src/lzma.rs`, written from those public-domain specifications and tested against CPython's `lzma` module (liblzma) output. The blobs were first recognised because their compressed bytes started with `5d 00 …` after an LZMA2 chunk header (`e0`/`e1` control byte, sizes, properties `0x5d` = lc 3, lp 0, pb 2), and CPython's `lzma` (FORMAT_RAW, FILTER_LZMA2) decompressed them. Nothing about Chromeleon was taken from prior art.

**Corpus files used:** the six development archives already listed above (`cmbx-lauterbach-invivo-cascade`, `cmbx-lauterbach-plate-screening`, `cmbx-lauterbach-repuox`, `cmbx-figshare-milks-sugars`, `cmbx-figshare-sugars-qev`, `cmbx-lim-tsoye-48h`), the PDF report `cmbx-lauterbach-invivo-report` and the six ASCII exports `cmbx-figshare-milks-export-*`.

**Inferred from the files:**
- **Object graph of the sequence file.** Top-level field 18 records are a catalog, one per object: 3 → 3 the type name (`Sequence`, `Injection`, `Signal`, `Chromatogram`, `AuditTrail`, `ProcessingMethod`, `InstrumentMethod`, `ReportDefinition`, `DataPresentationLayout`), 5 the object's GUID, 6 its parent's GUID (a GUID is a message of two fixed64 fields, 1 and 2, whose 16 little-endian bytes are the GUID's bytes), 8 the object's number in the data vault (the `662` of an export URL's `662.smp`). Top-level field 19 records hold the objects' data in the same order: field 25 = the object's GUID, 28 = its name, 27 = a version string, and one type-specific field (21 sequence, 19 injection, 5 signal, 18 chromatogram, 5 audit trail, 14/41/43 processing method, 11 instrument method). A chromatogram's parent is a signal, whose parent is an injection. The signal record's field 5 → 6 is the signal's `RawDataFileId`, which links it to header.xml and to its member.
- **Compressed blobs.** Byte strings starting with a 4-byte magic, `D?AC` (`DIAC`, `DdAC`) or `Cp??` (`CpXm`, `CpAu`), then a u16 header length (16, 16, 8, 20) and a u16 version (1, 1, 1, 2); when the header is at least 16 bytes long, a u32 compressed length and a u32 decompressed length follow (a `CpAu` header has one more u32). After the header: one LZMA2 dictionary-size byte (as in the `.xz` LZMA2 filter properties) and a raw LZMA2 stream. Every blob decompresses to UTF-8 XML beginning `<CmData>` and, where the header states it, to exactly the stated length: all 870 blobs inside the six sequence files and all 283 audit-trail members (one more member is damaged as deposited, see above): `DIAC` additional item data, `DdAC` processing-method settings, `CpXm` instrument methods (the instrument's symbol table and the method script), `CpAu` audit trails.
- **Audit trail members (`CpAu`).** The `.raw` members of `AuditTrail` items are such blobs: `<CmData><Messages><Item type="AuditTrailMessage">` with `Level`, `Category`, `Time` (ISO 8601 with offset), `Message`, and for device properties `Device`, `PropertyName`, `PropertyType`, `PropertyValue`, `PropertyUnit`. Earlier we had described them as possibly encrypted: they are only compressed.
- **Injection records (field 19 of the object's record).** 3 → 3 injection type (`Unknown`, `Standard`, `Blank`), 4 → 3 status (`Finished`, `Interrupted`), 5 position (`GA8`, `1`), 6 volume (f64), 7 → 1 inject time (ISO 8601 with offset), 2 calibration level name (`1`–`4` on standards), 9, 10, 11 three f64 that are 1.0 in every corpus injection, 17 a GUID string; fields 40 link the processing method (40.1 = 0) and the instrument method (40.1 = 1) by name. Checked against the six ASCII exports: `Position` (GA8, GB1, GD6, GE4, BA8, BB6), `Volume (µl)` 10.0 and `Inject Time` (e.g. `5/07/2024 7:38:21 PM +10:00` = `2024-07-05T19:38:21+10:00`) equal. The exports print `Dilution Factor` 1.0 and `Weight` 1.0; which of fields 9–11 is which cannot be told while all three are 1.0, so they are reported only when all three are equal (then each is that value).
- **Chromeleon's integration results (`ChmData.` blobs).** A chromatogram's catalog record holds, in field 16, a blob starting `ChmData.` then `01 vv 00 00` (vv = 1 in Chromeleon 7.2, 2 in 7.3.1), `01 00 00 00`, `67 00 00 00`, `01 00 00 00`, three length-prefixed 32-byte values (hash-like, not reproduced; perhaps keys of the inputs the results were computed from), then sections of u32 tag + u32 length: tag 2 the peaks, tag 3 (63–149 bytes) and tag 4 (8 bytes) not decoded. Tag 2: 8 zero bytes; a count (7-bit variable length) of skim lines, each a type byte (0) and two (time, value, slope) triples of f64 (the slope equals the line's slope between the two points); a count of peaks; per peak the start (time, value) and end (time, value) as f64 (values on the signal), a u32 code, the apex (time, value), for each side (leading, trailing) eight optional values (a presence byte 0/1 before each): unknown (always absent), the point at 10 % height, at 50 %, at 5 %, unknown (always absent), a point on the flank and a slope (the flank's tangent; exact meaning not established), unknown (always absent); then retention time, area and height (f64); a byte 0/1 and, when 1, an optional 16-byte component key and optional (expected retention time, a second component value) pair and a byte (the 1-based skim line the peak rides on, 0 for none); after the peaks a count of baseline segments, each a count of (time, value) points. Everything parses to the section's exact end on all 3,795 stored peaks.
- **Meaning, confirmed on every peak:**
  - The PDF report (57 injections, 118 pages) prints for 15 peaks retention time, area and height: all 15 equal the stored values to the printed 3 decimals; the 42 report pages without peaks are injections whose blob has no peaks (35) or no blob (7 injections at the end of the sequence, which the report shows with its own results: Chromeleon had not saved results for them).
  - Recomputing each stored peak from our decoded signal: area = trapezoidal integral of (signal − baseline) between the stored start and end (both on sample times), baseline = the baseline segment containing the peak (piecewise linear through its points) or, for a peak with a skim byte k > 0, the straight skim line k; for a peak with riders, minus the areas of the rider peaks inside it; height = signal − baseline at the apex. All 3,795 peaks (200 stored result sets in the six archives, peaks in four of them; 3 depositors; Chromeleon 7.2.10 and 7.3.1) agree: area within 4·10⁻¹¹ relative, height within 1.4·10⁻¹⁴; one negative peak (below its baseline) is stored with the positive magnitude. The stored 10 %, 50 % and 5 % points lie at exactly 0.10, 0.50 and 0.05 of the height above the baseline on every peak (554 to 1,058 stored points of each kind).
  - Component key: equals field 4 of the processing method catalog's `Component` entries (the processing method's catalog record, field 17: 1 = the component's GUID, as stored in field 10 of the component in the method's field 43 → 2 list, 2 = `Component`, 4 = this key); the component's name is field 12, its expected retention time field 5 → 2 → 9 and its second value field 5 → 2 → 14 — the pair the peak repeats. Every identified peak (409) maps to one component by this key, and its stored pair equals that component's (retention time, second value).
- **Processing method components** (processing method record field 43 → 2): 12 name, 10 GUID, 5 → 2 → 9 retention time (min), 5 → 2 → 6 amount unit (`mM`, `ppm`), 22 → (`Components.ConcentrationLevelCollection`) per level a level key (`LV…`) and the amount (f64 in field 3).

## 2026-09-26 — more archives: 3D fields, two more point encodings, rate denominators (Richard Zimring with Claude as assistant)

**New corpus files** (licences read from each record's Zenodo API metadata on 2026-09-26; none is in the held-out manifest):
- `cmbx-textiles-2019-088` — Zenodo 14002962 (Iacconi, Proaño Gaibor et al., Rijksdienst voor het Cultureel Erfgoed), `2019-088.cmbx` (362,007,765 bytes, md5 `462b1d403939270f36bd87e61e2ecaf8`), **CC-BY-4.0**; Chromeleon 7.2.9.11323, two UHPLC-PDA-HRMS injections (Waters Acquity PDA through `Acquity.dll`, Thermo Orbitrap).
- `cmbx-flavokawain-skrining-20221109` — Zenodo 10911597 (Chlipała, Tronina et al.), `2022.11.09 Skrining.cmbx` (361,535,243 bytes, md5 `691f8ed29cd1df6445c0d13ea72e9883`), **CC-BY-4.0**; Chromeleon 7.2.10, 78 UPLC-DAD injections (Thermo DAD-3000).
- `cmbx-lim-levodione-calibration`, `cmbx-lim-carvone-standards`, `cmbx-lim-r-carvone-reactions` — three more archives of Zenodo 10798153 (the record of `cmbx-lim-tsoye-48h`), **CC-BY-4.0**, md5 equal to the record's.

**Inferred from the files:**
- **`PtsLDiff` header.** The first of the four header integers, always 1 in the first six archives and read as a version then, is a rate denominator: the textiles archive's pump flow has 10000 and 600000 (60 points per minute: 2,401 points over 40 min, as its description says), its pressure 1000 and 600000 (10 Hz: 24,001 points). Points per minute = second / first; both signals equal their descriptions (point count, first and last time, minimum, maximum). The spectra of 3D fields use the same header for their wavelength grid (12 and 10: 1.2 nm; 10 and 10: 1 nm).
- **`PtsLL2Df`** (every DAD-3000 channel of the flavokawain archive): f64 6·10¹⁰ (time ticks per minute, i.e. nanoseconds) and f64 10⁸ (value units; the description's scale factor is 10⁻⁸), then integer pairs in the `PtsLDiff` code: (time, value) absolute, then first differences, then second differences, a final 0. The archive's first block holds only (0, 0). Decoded, all 520 signals (6 per injection plus pump pressure) equal their descriptions: 9,001 points from 0 to 6 min at 25 Hz, the recorded minimum and maximum exactly (e.g. −137.07797928 and 304.15622082 mAU).
- **`PtsDDCmp`** (textiles): integers 1, 0, the decompressed and the compressed length, then an LZMA2 dictionary byte and raw LZMA2 decompressing to (time, value) f64 pairs, blocks of 10,000 pairs. PDA-extracted channels (EXT350NM, EXT450NM, EXT600NM: 48,001 points, 20 Hz) and MS extracted-ion chromatograms (2,558–2,590 points at the MS scan times, `StepMin` ≠ `StepMax` in their descriptions) equal their descriptions.
- **Signals without a member** (textiles: 10 MS channels such as `Carminic acid_9.55 min_[491.08551, 500 MMU]`): no `RawDataFilename`; Chromeleon computes them from the MS data on demand. Not traces.
- **3D fields (`.sfd`).** `3DRawSpc`, u32 1, u32 0, u32 spectrum count (9,000; 48,001), u32 8; per spectrum f64 time, u32 length, a `RawSpHdr` section (repeating the time) and a `PtsLDiff` spectrum whose f64 is the first wavelength (220 nm; 200 nm). The sequence file describes a field in field 4 of the record (5 time, 6 wavelength range in nm, 7 absorbance range in mAU). All 80 fields decode whole to their stated count, their first and last time, wavelength range and minimum and maximum absorbance exactly. Checks that do not rest on our reading of the field alone: in the textiles archive Chromeleon stored the channels it extracted from the field (EXT350/450/600NM, a different encoding): each equals the field at the grid wavelength nearest its label bit for bit (6 channels × 48,001 points; 350 nm is on the 1.2 nm grid, 450 and 600 nm take the nearest point, not an interpolation). In the flavokawain archive the DAD also records its own channels (UV_VIS_2–6 at 254–400 nm, 4 nm bandwidth per the instrument method): the field averaged over ±2 nm agrees with each (slope 0.993–0.9996, r ≥ 0.99997 over 9,000 spectra of one injection), which confirms the scale (mAU) and the time axis independently of Chromeleon's software.
- **`SignHdr`.** The byte before the name length is 2 in the first archives, 3 (DAD-3000 channels) and 5 (PDA, MS channels) in the new ones: read as a kind byte, not checked.
- **File ids.** A day folder may be `DD_2` (textiles). A file id is not always the injection's start: the textiles archive's ids name 2020 and 2024 (the data were copied or derived later) while its inject times are in 2019; `check` compares a signal's start with its file id only when the id's time equals the injection's stored inject time (within 10 minutes).
- **Audit trails** of the flavokawain archive hold several `<CmData>` documents one after the other (108,273 messages in 78 trails).
- **Stored results** on the new archives: all 1,230 (flavokawain), 186 (textiles) and 68 + 21 + 60 (Lim) stored peaks reproduced by our integration within 1e-6 (areas; a stored height of 0 against a rounding residue below 1e-15).

**Prior art.** None consulted; LZMA2 as above.
