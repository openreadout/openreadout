# Provenance log — Hamamatsu DCIMG (`dcimg`)

Rules: `docs/legal/clean-room-policy.md`. Each entry: date, who, corpus files, prior art (URL + license), what was inferred.

## 2026-09-23 — reader (Richard Zimring with Claude as assistant)

**Prior art read (permissive):** `dcimg` 0.6.0.post1 by Giacomo Mazzamuto, MIT (https://github.com/lens-biophotonics/dcimg, installed in `oracle/.venv`; licence checked in the package metadata and repository). Read as documentation: the file header (magic `DCIMG`, format version 7 or 0x1000000, session count, frame count, header size, file size twice); the version-7 session header (frame count, bytes per pixel, width, bytes per row, height, bytes per frame, offset to the data, session data size) and session footer (offset of a second structure holding offsets to the frame counters, the time stamps and the stored correction pixels, the correction pixels' offset in the frame and size); the 0x1000000 session header (frame count, bytes per pixel, width, height, bytes per row, bytes per frame, 64-bit offset to the data) and its per-frame trailer (frame counter, time stamp seconds and microseconds, four stored pixels); time stamps as seconds plus microseconds since the Unix epoch; and the "4-pixel correction": the first four pixels of one line of every frame hold junk and their real values are stored separately. Names in our code are ours.

**Bio-Formats as a black box:** Bio-Formats 8.5.0 `showinf -omexml` and `bfconvert` (oracle/bftools, `-Xmx2g`) were run on each corpus file, each copied alone into an empty directory (with its siblings present Bio-Formats groups `<stem>_NNN_NNN.dcimg` files into one Z stack). Observed: frames become T, pixel type uint16, no physical sizes, only `Version` as original metadata; its planes are the stored rows in reverse order (bottom row first) with the four junk pixels replaced by the stored values. Our reader keeps the stored row order (like `dcimg` and like every other reader here: stored values, stored order); the oracle flips Bio-Formats' planes back before hashing and records that it did so.

**Corpus files used** (all CC-BY-4.0; OME sample images `DCIMG/`, each directory's `readme.txt` and `COPYING` checked; the Zenodo records' licence field agrees): Zenodo 14281237 "10 frames of fluorescent particles" (Zach Marin, Maohan Su; `Cell07_642_000_000.dcimg`, version 7, 10 frames of 2048 × 168 uint16), Zenodo 14268554 "Aberrated Bead Stack" (Zach Marin; `bead_bot4__560_00000_000NN.dcimg`, version 0x1000000, one 2048 × 200 frame each, 16-byte frame trailer, ORCA-Fusion `C15440-20UP`), Zenodo 14287640 "Astigmatic 4Pi bead stack" (Zach Marin, Maohan Su; `Cell09_642_000_NNN.dcimg`, version 0x1000000, one 2048 × 168 frame each, 32-byte frame trailer with stored pixels, ORCA-Flash4.0 `C11440-22C`). Bead and cell samples; no human material.

**Observed (hex dumps):**
- File header: `DCIMG\0\0\0`; u32 at 8 = 7 (`Cell07`) or 0x01000000 (the others); u32 at 0x20 = 1 (sessions); u32 at 0x24 = frames (10 / 1); u32 at 0x28 = 0x78 / 0x70 (header size = offset of the session header); u64 at 0x30 and again at 0x40 = the file size.
- Version 7 session header at 0x78: u64 session size; u32 frames (+0x20), bytes per pixel 2 (+0x24), 1 (+0x28), width 2048 (+0x2c), bytes per row 4096 (+0x30), height 168 (+0x34), bytes per frame 688128 (+0x38), offset to the data 112 (+0x44), u64 112 + 10 × 688128 (+0x48). Frames follow each other without gaps.
- Version 7 footer at header size + that u64: u32 7, u64 0xa0 (offset of a second structure), u32 at +0x28 = 0x1d8 (footer size). The second structure holds, as `dcimg` documents, the footer-relative offsets of the frame counters (+0x30 = 0x110), the time stamps (+0x40 = 0x138) and the stored pixels (+0x58 = 0x188) — each also reachable through a pointer at +0x10, +0x00 and +0x20 — then the stored pixels' offset in the frame (u32 +0x64) and their size (u64 +0x68). The frame counters (0, 1, … 9) are u32 at footer + 0x110, the 8-byte time stamps at footer + 0x138 (u32 1511904855 s + 664884 µs = 2017-11-28T21:34:15.664884Z: the acquisition PC's clock, the deposit is from 2024), the stored pixels at footer + 0x188 (four u16 per frame), their offset in the frame 0x53000 (= row 83 × 4096 bytes, column 0) and size 8. Row 83 of every frame holds `0, 65535, 0, 65535` in its first four pixels: the junk.
- Version 0x1000000 session header at 0x70: frames at +0x3c, bytes per pixel +0x40, width +0x48, height +0x4c, bytes per row +0x50, bytes per frame +0x54, u64 offset to the data +0x60, frame stride (bytes per frame + trailer) +0x74, trailer size +0x7c (16 in the bead files, 32 in `Cell09`). A table of 16-byte entries (u32 kind, u32 size, u64 offset relative to session header + 0xa0) at +0xf0 lists contiguous blocks; the block of 248 bytes holds NUL-padded text at +0x00 (`24.6.4322.6822` / `19.12.642.5901`), +0x20 (`1.2.6.6822` / `7.5.140.5901`), +0x40 (camera model `C15440-20UP` / `C11440-22C`), +0x80 (`1.14` / `2.50.A`), +0x90 (`S/N: 501542` / `S/N: 001634`) and four u16 at +0xc8 (sub-array: x 0, width 2048, y 1004 / 940, height 200 / 168). Only `Cell09` has a kind-4 block (56 bytes: 1, 0, 16, 8, 0x53000, 1, …) holding 0x53000 and 8 — the same in-frame offset and size as the version-7 footer — and only it has the junk pattern in row 83 = 1023 − 940; its 32-byte trailer holds the real values at +12. The bead files' row 19 (= 1023 − 1004) is ordinary data and their 16-byte trailer has no pixels.
- Time stamps compared with the deposit: `Cell09` frame 0 is 1725555197 s = 2024-09-05T16:53:17Z, and its `Cell09.txt` says "9/5/2024 12:54 PM" (US Eastern daylight time): the stamps are UTC.

**Inferred (flagged in the format notes):** the meaning of the text fields other than the model and serial (software / firmware versions: the reader lists them as they are); that the kind-4 block announces the stored pixels (one file has it and the pixels, two have neither); that the pixel count is the block's size ÷ bytes per pixel; the sub-array block location (the same +0xc8 in two files with different table lengths).

**Bio-Formats and dcimg disagreements found (black-box observations):** in the version-7 file Bio-Formats puts frame 0's stored values into the overwritten pixels of every frame (the footer table holds four different values per frame; frames 1–9 differ from dcimg in exactly those 4 pixels); `dcimg` reads the version-0x1000000 files' sub-array from a fixed offset (session header + 712) that these files do not use, so it neither places nor applies the stored pixels there, and it assumes a 32-byte trailer when striding frames. The oracle (`oracle/gen.py` `dcimg_`) therefore takes version-7 planes from `dcimg` and version-0x1000000 planes from Bio-Formats (rows flipped back), and records the other reader's disagreement in pixels (`bioformats_diff_pixels`, `dcimg_raw_diff_pixels`). `dcimg` 0.6.0 needs a small NumPy-2 shim to run at all (one-element structured arrays passed to `int()`); the shim changes no decoding.

**Validation (2026-09-23).** Corpus harness: 15 files, 24 planes bit-exact, 24 frame records (camera counter and UTC time stamp) equal to `dcimg`'s. Synthetic tests (`crates/openreadout-dcimg/tests/synthetic.rs`): both layouts with and without stored pixels, a dropped frame (`frame_counter_gap`), files cut inside a frame (`check` error `truncated`, the cut frame's read exits 4) and inside the headers (open exits 4), and byte flips in the first KiB (no panic).

## 2026-09-25 — assurance profile (`src/assurance.rs`)

**Corpus files:** every development input of this format on disk (`corpus/assurance/evidence.json` lists them); no held-out file.
**Prior art consulted:** none.
**What was done.** No parsing logic changed. The reader declares an assurance profile (docs/assurance.md) that fingerprints each file from this reader's own normalized output: the frame layout, binning, the restored overwritten row pixels (reported as an applied correction) and truncation. The table of validated feature values and the confidence level are generated from the development corpus by `cargo xtask assurance-audit`.
